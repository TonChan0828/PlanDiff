## 10:00 PWA起動時に毎回ログインを求められる不具合の調査と修正(P3-3 M2)

- 発端:
  - ユーザーから「スマホ(iPhone)でホームに追加したが、起動するたびにログインが求められる」との報告。
    P3-3 の M2(実機確認)を実施したことで発覚した
- 調査でわかったこと:
  - **セッションは失われていない**。切り分けとしてユーザーに「起動後に『ログイン』を押すとどうなるか」を
    確認したところ、**入力を求められず即 `/calendar` へ遷移**した。
    `app/(marketing)/login/page.tsx` のログイン済み判定(`getUser()` → `redirect("/calendar")`)が
    成功しているということなので、cookie も refresh token も生きている
  - 真因は `app/manifest.ts` の **`start_url: "/"`**。`/` は `app/(marketing)/page.tsx` の
    マーケティングLPで、**認証状態を一切見ない静的ページ**。ログイン済みかどうかに関係なく
    「無料で始める / ログイン」のCTAを出す(`components/marketing-header.tsx` も同様)。
    PWAは起動のたびに `start_url` を開くため、毎回このLPが出て「ログインが求められる」ように見えていた
  - 認証・cookieの不具合ではなく、**PWAの起動先の設定ミス**だった
- あわせて見つかった副次リスク(同じ修正で解消):
  - `proxy.ts` の matcher は `/` を除外している(P6-1でLPの静的配信を守るための判断)。
    そのため**LPしか開かない限りサーバー側のセッションリフレッシュが一度も走らない**。
    iOS Safari の ITP は `document.cookie` 由来のcookieを7日で失効させるため、
    `lib/supabase/browser.ts` が書いたauth cookieは `proxy.ts` の `getUser()` が
    `Set-Cookie` を打ち直して初めてこの上限から外れる。放置すれば**実際に**ログインが切れていた
  - cookie 側の設定に不備はないことも確認済み。`@supabase/ssr@0.12.0` の
    `DEFAULT_COOKIE_OPTIONS` は `maxAge: 400日` を持つ(`node_modules/@supabase/ssr/dist/main/utils/constants.js`)。
    `cookieOptions` の明示指定は不要と判断した
- やったこと(TDD: Red → Green):
  - 先に `tests/app/manifest.test.ts` を更新(S1 の `start_url` 期待値変更、S8/S9 追加)して失敗を確認
  - `app/manifest.ts` を修正:
    - `start_url: "/" → "/calendar"`(起動先を認証必須グループ配下にする。未ログインなら
      `app/(app)/layout.tsx` が `/login` へ送るので初回インストール時の挙動も正しい)
    - `id: "/"` を追加(`id` の既定値は `start_url`。明示しないと `start_url` 変更で
      Chromeが別アプリと認識し、既存インストールが更新されず二重登録になる)
    - `scope: "/"` を追加(既定scopeは `start_url` のディレクトリ。ログアウト先の `/login` などが
      scope外に落ちて外部ブラウザで開かれる事故を防ぐ)
  - `docs/specs/P3-3_PWA対応.md` を改訂: §1 のmanifest定義と根拠、S1改訂・S8/S9追加、
    M2-a/b/c(実機の再確認手順)を追加
  - `docs/開発計画.md` の P3-3 行と「次に着手」§5 を更新
- 採用しなかった案:
  - **LPでログイン済みを判定して `/calendar` へリダイレクト**: `/` が動的レンダリングになり、
    LPを静的配信のまま保つP6-1の判断に反する。訪問者全員にSupabase Authへの往復を課すコストに見合わない
