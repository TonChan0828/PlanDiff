## 08:05 P12-1 実装(Red → Green)

- やったこと:
  - Red: 仕様のS1〜S12に対応するテストを既存5ファイルに追加(計13件)。全件失敗を確認
  - Green: `components/calendar-view.tsx` に `useTransition` を1本(`viewPending`)導入
    - 共通ヘルパー `startViewUpdate(update)` を新設し、`startViewTransition(async () => { await update() })` で包む
    - ラップ対象12箇所: `handleNavigate` / `handleToday` / `handleViewChange` /
      週ヘッダー`onClick` / `WeekStrip.onSelect` / 予定・実績の保存・削除7ハンドラの成功時 `router.refresh()`
    - 対象外(仕様どおり): タイマー系(既に楽観的更新済み)・`handleSaveStart`・
      同期`useEffect`・日付またぎ`useEffect`
    - UI: ナビ系ボタンに `disabled={viewPending}` + `disabled:opacity-50`、日付ラベル横に
      `Loader2` スピナー + `role="status"` の sr-only テキスト、グリッドに
      `aria-busy` + `pointer-events-none opacity-60`、`WeekStrip` に `pending` prop 追加
    - `lib/calendar/messages.ts` に `viewUpdatingLabel: "表示を更新しています"` を追加
      (Google同期の `syncing` とは別状態なので流用しない)
- 理由:
  - **`await update()` を挟む設計判断**: `router.push`/`refresh` は本番で `void` を返すため、
    素の `startTransition(() => ...)` だと React がトランジション内に待つべき非同期処理を
    見つけられず `isPending` が即 false に戻る。React 19 の非同期トランジションにすることで
    RSC再取得のコミットまで pending を保てる(テストでも制御可能なPromiseで再現できる)
  - グリッドに `pointer-events-none` を付けるのは、反映待ちの間は古いデータが残るため、
    予定ブロックの誤タップでタイマーが動くのを防ぐため
- 結果:
  - `npm run check` 合格(EXIT=0)。**761件全合格**(P12-1で+13件)
  - `calendar-view*` 系8ファイル86件が全合格(タイマー/再計測/オーバーレイの回帰確認S13/S14含む)
  - R-1: `TZ=UTC` / `TZ=Pacific/Kiritimati` の両方で65件合格を確認済み
- **テスト実装中の発見(重要)**: 非同期トランジションを扱うテストは「後始末」まで含めて1件。
  未解決のままアンマウントしたPromiseが**次のテストを失敗させる**(S7を解決せずに終えるとS8が
  aria-busy=true のまま戻らなくなった)。各テスト末尾で `deferred.resolve()` して解消。
  併せて、`googleEnabled` 既定 `true` だとマウント時の同期が先に `router.refresh()` を呼び
  `mockReturnValueOnce` を消費してしまうため、P12-1のテストは `googleEnabled={false}` で描画する
- 未解決・次にやること: 375px の手動確認
