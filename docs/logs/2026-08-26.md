## 08:05 PR #73 のCI失敗 — 既存フレーキーテストの修正(S-1に内包)

- やったこと:
  - PR #73 を作成(https://github.com/TonChan0828/PlanDiff/pull/73)。初回CIが `npm test` で失敗
  - 失敗は `tests/components/calendar-view.test.tsx` の
    「S7: 時間軸上にタイトル・時刻付きの予定ブロックが表示される」1件
    (`TestingLibraryElementError: Found multiple elements with the text: 23:00`)
  - 原因を特定: 時間軸ラベルは `${hour}:00`(`components/calendar-view.tsx:1043`)、
    現在時刻チップは `format(now, "HH:mm")`(同 `:1371`)。**`hour >= 10` の毎正時0分台の
    1分間だけ**両者が同じ文字列になり `getByText` が複数一致する。
    9時台は `"9:00"` と `"09:00"` で衝突しないため長く隠れていた
  - `tests/setup.ts` を一時的に細工して `setSystemTime(23:00)` → **失敗を再現**、
    `setSystemTime(12:00)` → 29件全合格。細工は元に戻した(git差分なしを確認)
  - ユーザーに扱いを確認 → 「S-1のPRに含める / 該当ファイルのみ固定 / R-1を更新」で承認
  - `tests/components/calendar-view.test.tsx` のトップレベル(`const today` より前)に
    `vi.useFakeTimers({ shouldAdvanceTime: true })` + `vi.setSystemTime(正午)` を追加
  - CLAUDE.md の **R-1 を「発生3回」→「発生4回」に更新**し、再発防止項目を追記

- 理由:
  - **依存更新とは無関係の既存バグ**。CIがちょうど UTC 23:00台に入って踏んだだけで、
    発生窓は 10:00〜23:00 の各正時0分台=1日あたり14分しかない
  - R-1 は既にあるが「TZを固定する」までしか書いておらず、**「時刻を固定する」が抜けていた**。
    今回はTZ由来ではなく時刻由来のため、既存ルールを読んでも防げなかった。
    だからルール自体を強化した(CLAUDE.md 開発方針7)
  - `beforeEach` ではなくモジュールトップに置いたのは、`const today = startOfDay(new Date())` が
    import 時に評価されるため。`beforeEach` では間に合わない
  - 修正対象を1ファイルに留めたのは、`getByText("H:00")` 形式のアサーションを持つのが
    このファイルだけだと調査で確認できたため。`tests/setup.ts` で全128ファイルに
    fake timers をかける案は、既に `setSystemTime` を使う8ファイルと干渉するリスクを避けて採らなかった

- 結果(テスト・ビルドの出力要約):
  - 修正後 `tests/components/calendar-view.test.tsx`: `TZ=UTC` / `TZ=Asia/Tokyo` /
    `TZ=Pacific/Kiritimati` の**3TZすべてで29件全合格**。固定時刻になったため実時計に依存しない
  - 注意: 検証の途中で `tests/setup.ts` に `setSystemTime` を入れたまま修正後のファイルを
    走らせると9件失敗する。これは fake timers の**二重適用による計測の副作用**であり、
    修正の不備ではない(実時計の下では二重適用は起こらない)
