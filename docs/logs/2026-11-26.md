## G-112 の競合が残っていた不具合の修正

- 発見: ドキュメントのみの PR #131 の CI で、結合テスト B8(同じ期間を同時に2回表示)が失敗した。今日以降の行に調整前の時刻(`00:00Z`)が残っていた。
  #129 のマージ時の CI とローカルでは合格しており、割り込みの時機に依存する
- 原因: 再実体化が「①上書き対象の既存行を確認 → ②挿入のみ → ③上書き」の順だった。①と②の間に別リクエストが調整前の行を入れると、①の対象に含まれず、②では重複として無視されて残る
- 対応: 先に全行を挿入のみで書き、そのあとで確認して上書きする順にした。挿入後は全ての回に行があり、遅れて届く古い挿入は無視される
- 再現: メモリ上の表で、`synced_events` への各操作の直前に古い挿入を割り込ませるテスト(`recurring-overwrite-race.test.ts`)を作り、
  修正前は「確認と挿入の間」の1ケースだけが失敗することを確認した。修正後は全ケース合格。結合テストは8回連続で合格
- 見逃した理由: #129 のレビュー2周と私の検証は、「調整の削除のあとに古い挿入が入る」順序(B10)だけを固定していた。確認してから書く処理は、
  **確認と書き込みの間の割り込み**を疑うべきで、割り込み位置を網羅するテストを最初から作るべきだった。B8 は偶然の時機に頼るため、数回の実行では検出できなかった
- 本番への影響: #129 のマージ後に公開されている。起きるのは、同じ週を同時に表示した瞬間に自動調整が適用された場合に限られ、症状は #129 以前からあった競合と同じ(古い時刻の予定が残る)
- 環境メモ: 再起動後は Docker が停止しており、結合テストが全件 skipped と表示された(合格ではない)。Docker Desktop を起動してから実行した
- レビュー(周1): minor 1件のみ(R1: 今日の回を後の時刻へ個別編集済みの場合の残り。今回の変更より前からある経路で、解消には DB 変更が要る)→ 仕様書の「残る限界」に追記
