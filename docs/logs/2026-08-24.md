## 計測しっぱなし(12時間超)の検知と通知 — 仕様書作成(P13-1)

- やったこと:
  - ユーザー要望「12時間以上計測しているものは操作忘れだとし、通知やメールする機能を実装したい」を
    ブレインストーミング(`superpowers:brainstorming`)で architectural と分類し、要件を確定
  - **現状調査で3つの前提を確認**:
    - 通知基盤がゼロ(`vercel.json`/`vercel.ts` なし=cron未設定、メール送信ライブラリなし、
      Service Worker がリポジトリに1つも存在しない)
    - `docs/specs/P3-3_PWA対応.md:74` で Service Worker を**意図的にスコープ外**にしていた
    - タイムゾーンが Cookie にしかなく(`components/timezone-sync.tsx`)、`profiles` に TZ 列がない。
      **cron はリクエストを持たないため Cookie を読めず、ユーザーのTZを知る手段がない**
  - **Vercel Cron の Hobby 制限を公式ドキュメントで実確認**
    (https://vercel.com/docs/cron-jobs/usage-and-pricing): ジョブ数100本、
    **最小間隔=1日1回、精度±59分**。Pro は分単位
  - **iOS の Web Push 制約を実確認**: ホーム画面追加した PWA でのみ動作(2026年時点でも変更なし)。
    Safari タブでは `PushManager` 自体が存在しない
  - `.claude/skills/db-migration` を呼び出し、テーブル追加のRLS/GRANTパターンを既存
    (`google_tokens` / `pro_interest_events` / P6-5)に合わせて設計
  - `docs/specs/P13-1_計測しっぱなしの検知とPush通知.md` を作成(承認待ち)
  - `docs/開発計画.md` に Phase 13 と P13-1 を起票、「次に着手」の先頭に追加
- 理由(ユーザーとの合意で決めたこと):
  - **配信は Web Push のみ、メールは実装しない**: 外部メール送信サービスの契約・独自ドメイン認証が不要。
    PlanDiff は独自ドメイン未取得(plandiff.vercel.app)で送信元アドレスの用意が論点になるため
  - **検知は1日1回**: この選択により Vercel Hobby のままで成立し、Pro へのアップグレードも
    Supabase `pg_cron` の導入も不要になった。毎時チェックを選んでいたらどちらかが必須だった
  - **自動停止はしない**: 本当に長時間作業した記録を壊すリスクを避ける
  - **通知は1計測につき1回**(`time_entries.stale_notified_at` で管理): 自動停止しないため
    毎日鳴らすと「催促」になり、通知自体を切られる
  - **`push_subscriptions` はポリシーを一切作らない**: endpoint と鍵は「その端末へ任意の通知を送る権限」
    そのもの。かつ設定画面の有効/無効判定は `pushManager.getSubscription()` でブラウザ側から取れるため、
    クライアントがDBを読む必要が一切ない
  - **`vercel.ts` ではなく `vercel.json`**: cron 1本のために `@vercel/config` を足す価値がない
