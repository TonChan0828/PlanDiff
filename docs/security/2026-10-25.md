## 1. 高：Next.js の既知のサービス停止につながる脆弱性

**根拠**：使用中のバージョンは `next@16.3.8` です。アプリは App Router を使い、Server Action（ブラウザーから呼び出せるサーバー処理）を複数公開しています。公式告知 GHSA-p3m5-59mp-jv5r は、これらを使う対象バージョンに対し、細工したリクエストによってCPU使用量が増加し、同一プロセスの他のリクエスト処理を阻害できるとしています。修正版は `16.4.1` です。[Next.js告知 (2026/10), Impact・Patched versions]

コードの所在：

- [package.json:26](../../package.json#L26)
- [タイマー操作のServer Action](../../app/(app)/calendar/timer-actions.ts)
- [アカウント設定のServer Action](../../app/(app)/settings/actions.ts)

**影響の評価**：このアプリは告知に記載された対象条件を満たします。認証不要で攻撃できる脆弱性であり、各処理内のログイン確認では代替対策になりません。今回、サービス停止を起こす実証リクエストは送っていません。[Next.js告知 (2026/10), Exploitability Metrics・Impact]

**対応案**：互換性を確認したうえで Next.js と関連する `eslint-config-next` を更新します。今回の監査が提示した Next.js の更新先は `16.4.3` です。ロックファイルも更新し、型検査・静的検査・既存テスト・本番ビルドを実行してください。公式告知では更新以外の回避策は示されていません。[Next.js告知 (2026/10), Workarounds] [今回の監査結果](2026-10-25/npm-audit.json)

### 「緊急」と報告された他の2件との区別

`npm audit` は Next.js を「緊急」と集計しますが、このアプリで遠隔からの任意コード実行を確認したわけではありません。

- **画像最適化処理の問題 GHSA-2464-fhr4-w9xw**：公式告知は glibc を使うLinuxでの画像処理を対象とし、`sharp >= 0.35.5` を回避策としています。この作業ツリーの依存関係は `sharp@0.35.5` なので、この回避条件を満たしています。本番で使用中の依存関係は未確認です。[画像処理告知 (2026/10), Impact・Workaround]
- **キャッシュ処理の問題 GHSA-673q-mjm6-r5xr**：Cache Components と、複数の型付き配列を返す `use cache` 関数が条件です。アプリのコードと `next.config.ts` に該当する使用は見つかりませんでした。React の `cache()` によるリクエスト内の共有とは区別しています。[キャッシュ処理告知 (2026/10), Impact] [設定](../../next.config.ts) [認証クライアント](../../lib/supabase/server.ts)

## 2. 中：未認証の計測APIから書き込みを繰り返せる

**根拠**：料金ページの計測を受け付ける `/api/pro-interest` は、本文の `event` が `view` または `click` なら、管理者権限を使う保存処理を呼び出します。アプリ内に呼び出し回数の制限、送信元の検証、本文サイズの上限がありません。データベースの保存処理はリクエストごとに1行を追加します。[API処理:15](../../app/api/pro-interest/route.ts#L15) [保存処理](../../lib/supabase/admin.ts) [保存先テーブル](../../supabase/migrations/20260713035812_pro_interest_events.sql)

**再現結果**：実データベースの代わりに保存関数を代替処理に置き換え、API処理を直接呼び出しました。

- 認証情報なし、外部サイトの `Origin`、`Content-Type: text/plain` で100回呼び出すと、100回とも204応答になりました。保存関数も100回呼び出されました。
- 不要な文字列を1 MiB含むJSONも204応答になり、保存関数が呼び出されました。`Content-Length` がない場合です。

再現に使ったコードは [pro-interest-reproduction.txt](2026-10-25/pro-interest-reproduction.txt) に保存しました。テストは一時ファイルとして実行後に削除しています。

**影響の評価**：第三者が計測値を汚染できます。繰り返し送信による保存行数・処理回数・費用の増大も懸念されます。アプリ外の配信基盤に制限があるかは未確認なので、本番で無制限に保存できるとまでは断定しません。個人情報の読み取りや、他人のアカウントの変更ができる問題ではありません。

**対応案**：未認証での計測は維持しつつ、共有ストアまたは配信基盤を使って呼び出し回数を制限してください。本文は読み取り中にもサイズを制限し、想定するデータ形式と送信元を検証してください。送信元検証だけでは自動送信による乱用は防げないため、回数制限と併用します。参考となる既存実装として、[エラー報告API](../../app/api/monitoring/errors/route.ts) は本文サイズと送信元を検証しています。ただし、このAPIのプロセス内カウンターを複製するだけでは、複数の実行環境にまたがる上限にはなりません。

## 3. 中・条件付き：削除例外が他人の繰り返し予定を参照できる設計

**根拠**：`recurring_exceptions`（繰り返し予定のうち、特定の日だけを削除したことを保存するテーブル）の挿入・更新条件は、例外行の `user_id` が本人かだけを検証します。参照する `rule_id` が本人の繰り返し予定かは検証していません。外部キーは予定のIDだけを参照し、重複禁止の組み合わせは `(rule_id, occurrence_date)` です。[有効なRLS定義:130](../../supabase/migrations/20260807143501_range_index_and_policy_roles.sql#L130) [テーブル定義:51](../../supabase/migrations/20260713220814_recurring_events.sql#L51)

PostgreSQLでは外部キーや一意性などの参照整合性検査はRLSを迂回します。このため、参照先がRLSで見えないことだけでは、他人のIDの参照を拒否できません。[PostgreSQL文書 (参照2026/10), Referential integrity checks]

**攻撃条件と予想される影響**：これはマイグレーションとコードから判断した問題であり、今回のデータベースでの実証は未実施です。

1. ログイン済みの攻撃者が、被害者の繰り返し予定のIDを別の経路で知っている必要があります。今回、そのIDが他人に漏れる経路は確認していません。
2. 攻撃者はData APIへ直接、`user_id` に自分のID、`rule_id` に被害者のID、`occurrence_date` に対象日を指定して挿入します。
3. 被害者が同じ日の予定を削除すると、一意性違反になります。アプリは一意性違反を「既に登録済み」として成功扱いにします。[削除処理:439](../../lib/calendar/recurring.ts#L439)
4. 被害者の予定行は削除されますが、被害者の削除例外は保存されません。攻撃者の例外はRLSにより被害者から見えないため、後の予定生成で削除済みの予定が再び作成される可能性があります。[例外取得・予定生成](../../lib/calendar/recurring.ts)

**対応案**：挿入・更新時に、参照する予定の所有者も本人であることをRLSで検証してください。別案として、親テーブルの `(id, user_id)` を一意にし、子テーブルの `(rule_id, user_id)` を複合外部キーにする方法があります。既存の不整合行の有無も確認が必要です。修正時には、利用者Aが利用者Bの予定を参照する例外を挿入・更新できないことと、削除後に予定が復活しないことを結合テストで確認してください。

なお、新しい [休止期間のテーブル](../../supabase/migrations/20261018131510_recurring_pause_and_five_minute_learning.sql) には参照先の所有者を検証する条件があります。同じ条件を削除例外には確認できませんでした。

- アプリの設定内に、他サイトの画面内への埋め込みを制限する `frame-ancestors` や `X-Frame-Options`、読み込み可能なスクリプトなどを制限する Content Security Policy の設定は見つかりませんでした。配信基盤が追加しているかは未確認です。現段階では本番の脆弱性として数えていません。[Next.js設定](../../next.config.ts) [Proxy](../../proxy.ts)

## 確認できた防御

以下はコード・マイグレーション上の確認結果です。本番に同じ状態が反映されているかは別途確認が必要です。

- 更新処理は、それぞれで認証基盤への `getUser()` による本人確認を行います。[共通の本人確認処理](../../lib/supabase/session-user.ts) [Server Action](../../app/(app)/calendar/event-actions.ts)
- 主要な利用者データには本人の `user_id` によるRLSがあり、一般利用者から管理者専用テーブルへの権限は取り消されています。[RLS定義](../../supabase/migrations/20260807143501_range_index_and_policy_roles.sql) [権限の取り消し](../../supabase/migrations/20260808024737_revoke_anon_table_grants.sql)

- 通知の送信先はHTTPSの既知ホストに制限されています。外部入力から任意のサーバーへ通信させる問題への対策です。[送信先検証](../../lib/notifications/validation.ts)
