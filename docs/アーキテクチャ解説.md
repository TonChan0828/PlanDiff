## 1. プロダクト概要

**PlanDiff は「見積もりが当たるようになる、エンジニアのためのカレンダー × タイムトラッカー」**。

カレンダーの「予定(計画)」と、ワンタップで記録する「実績(現実)」を**同一タイムラインに重ねて表示**し、
計画と現実のギャップを可視化する。ターゲットはソフトウェアエンジニア個人。差別化の核は
「予定 × 実績のオーバーレイ表示」と「見積もりズレの定量化」であり、機能の広さでは戦わない。

### コアループ

```mermaid
flowchart LR
    A["計画する<br/>(予定を立てる)"] --> B["実行・記録する<br/>(タイマー)"]
    B --> C["ギャップを見る<br/>(オーバーレイ / サマリー)"]
    C --> D["次の計画が賢くなる<br/>(予定提案・学習補正)"]
    D --> A
```

このループの各段階が、そのまま実装の主要領域に対応する:

| 段階 | 主な実装 | 章 |
|---|---|---|
| 計画する | アプリ内予定 / 定期予定(`lib/calendar/`) | §7.3 |
| 記録する | タイマー(`lib/timer/`) | §7.1 |
| ギャップを見る | オーバーレイ(`components/calendar-view.tsx`)/ サマリー(`lib/summary/`) | §9, §10 |
| 賢くなる | 予定提案(`suggestions.ts`)/ 学習補正(`rule-learning.ts`) | §7.4, §7.5 |

### 重要な前提: Google連携は現在「凍結中」

もともとGoogleカレンダー連携を主導線として設計されたが、ドメイン取得・OAuth審査のリードタイムが
開発ボトルネックになったため、2段階の方針転換を行った
(経緯は要件定義書 §変更履歴、仕様書 [P1-3](specs/P1-3_メール認証とGoogle任意連携.md) / [P2-5](specs/P2-5_アプリ内予定とGoogle連携凍結.md)):

1. **メール認証(Supabase Auth)を主導線化** — Googleログインは提供しない
2. **Google連携UIを環境フラグ `GOOGLE_INTEGRATION_ENABLED`(既定OFF)で凍結** — 予定はアプリ内作成で完結

Google連携のコード・テストは削除されておらず、フラグをONにすれば復活する
(判定は `lib/google/integration-flag.ts` の1関数に集約されている)。
**現在の主導線は「メール認証 + アプリ内予定 + タイマー」**である。
この資料でもGoogle連携のフローを解説するが、動作させるにはフラグONが必要。

## 3. ローカル環境の立ち上げ

### 前提

- Node.js 22(CIと揃える。`.github/workflows/ci.yml` 参照)
- Docker(ローカルSupabaseの実行に必要)
- Supabase CLI(`npx supabase` で都度実行するため個別インストールは不要)

### 手順

```bash
# 1. 依存関係
npm ci

# 2. Gitフックを有効化する(これを忘れると品質ゲートが効かない)
git config core.hooksPath .githooks

# 3. 環境変数
cp .env.example .env.local
#    → 値を埋める(下表参照)

# 4. ローカルSupabaseを起動し、マイグレーションを適用する
npx supabase start
npx supabase db reset   # supabase/migrations/*.sql を頭から適用し直す

# 5. 開発サーバー
npm run dev             # http://localhost:3000
```

### 環境変数(`.env.example`)

| 変数 | 用途 | 入手元 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabaseのエンドポイント | `npx supabase status`(ローカル)/ ダッシュボード > Settings > API(本番) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 匿名キー。RLS前提でクライアントに露出してよい | 同上 |
| `SUPABASE_SERVICE_ROLE_KEY` | **service role キー。RLSを迂回する**。`NEXT_PUBLIC_` を付けない | 同上 |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google OAuth。**凍結中は未設定でよい** | Google Cloud Console |
| `SUPABASE_DB_URL` | 結合テストがRLSを介さずDBを直接検証するために使う | `npx supabase status`。ローカルの既定値は `.env.example` に記載済み |
| `GOOGLE_INTEGRATION_ENABLED` | `"true"` のときだけGoogle連携UI/APIが有効(§1) | 手動。**既定は未設定=凍結** |

### 動作確認

```bash
npm test                  # unit/component(125ファイル・761件)
npm run test:integration  # 結合(23ファイル・133件。ローカルSupabase起動が前提)
```

### 3つのSupabaseクライアント(`lib/supabase/`)

| ファイル | 用途 | 権限 |
|---|---|---|
| `server.ts` | Server Component / Server Action / Route Handler | ログインユーザーの権限(**RLSが効く**)。cookieからセッションを読む |
| `browser.ts` | Client Component | 同上(anonキー) |
| `admin.ts` | サーバー専用の特権処理 | **service role(RLSを迂回)**。`google_tokens` の読み書き、アカウント削除、pro-interest計測に限定。冒頭の `import "server-only"` により、誤ってクライアントバンドルに混入するとビルドエラーになる |

補助モジュール:

- **`session-user.ts`** — `auth.getUser()` の重複往復を抑えるヘルパー(P6-1)。
  `getUser()` は毎回HTTP往復でローカルキャッシュを持たないため、`WeakMap<SupabaseClient, Promise<User>>`
  でクライアントインスタンス単位に結果を保持する。**Reactの `cache()` を使っていない**のは、
  リクエストコンテキスト外(vitest)では素通しになり重複排除をテストで固定できないため
- **`paged-fetch.ts`** — PostgREST の行数上限(`max_rows`、既定1000)対策のページング取得(P6-0)。
  詳細は §11

### 責務の分離原則

- **Server Components がデフォルト**。ページ(Server Component)がDBからデータを取得し、
  propsでClient Componentに渡す。`"use client"` はインタラクションが必要な葉に限定
  (実際にはカレンダー・タイマー等のUIがほぼすべてクライアント側だが、**データ取得の起点は常にサーバー**)
- **Google APIの呼び出しはサーバーのみ**(`app/api/calendar/sync` に集約)。
  Googleのトークンは絶対にクライアントへ渡さない・ログに出さない
- `proxy.ts`(旧middleware)は**セッションの期限切れ更新のみ**を行い、認可判定はしない。
  未ログインのリダイレクトは `app/(app)/layout.tsx` が担当。
  マーケティングの静的ページ(`/`, `/pricing`, `/privacy`, `/terms`)は matcher から除外されている
  — 除外しないとLPを開くたびにSupabase Authへの往復が1回入る(P6-1)

### 認証済みシェル(`app/(app)/layout.tsx`)

わずか41行だが、押さえるべき点が3つある:

1. `export const dynamic = "force-dynamic"` — `cookies()` を呼ぶ前に環境変数チェックで例外を投げると
   Next.js の動的判定より先にビルド時プリレンダリングが走ってしまうため、明示している
2. `getSessionUser()` が `null` なら `/login` へリダイレクト — **認可判定はここが唯一の場所**
3. `<TimezoneSync />` を1つだけ配置 — 訪問者のTZをCookieへ同期する(§8)

レイアウトは `h-dvh` で固定し、コンテンツ領域を内部スクロールにしている。
これによりカレンダーのタイムラインが残り高さいっぱいに広がる(D-1d)。

### 表示状態はURLで持つ

カレンダーは `?view=day|week&date=yyyy-MM-dd`、サマリーは `?range=...&date=...`(customは `&from&to`)。
Reactのstateではなく**URLが表示状態の正**なので、リロード・共有・戻るボタンが自然に動く。
パースは `lib/calendar/view-date.ts` / `lib/summary/range.ts` の純粋関数に閉じている。

### 初見で押さえるべき3ポイント

**(1) `synced_events` には3種類の「予定」が同居する**

| 種別 | `source` | `google_event_id` の形式 | 作られ方 |
|---|---|---|---|
| Googleカレンダー予定 | `google` | GoogleのイベントID | `/api/calendar/sync` が upsert(凍結中は作られない) |
| アプリ内予定 | `app` | `app:<uuid>` | 予定作成パネルから `event-actions.ts` 経由で insert |
| 定期予定インスタンス | `app` | `rec:<ruleId>:<date>` | ページ表示時に `recurring_rules` からオンデマンドで冪等実体化(§7.3) |

この設計により、タイマー・オーバーレイ・サマリーは「`synced_events` にある行 = 予定」とだけ考えればよく、
予定の出自を意識せずに動く。Google由来の予定は読み取り専用(`source` ガードで改変不可)、
同期時のstale削除も `source='google'` の行だけが対象なのでアプリ内予定は消えない。

> **将来の設計課題**: `rec:<ruleId>:<date>` の文字列パースをやめて
> `synced_events.recurring_rule_id` 列に正規化するのが本命だが、既存データの移行を伴うため見送り中
> (`docs/開発計画.md` Phase 6 スコープ外に記録)。

**(2) 予定と実績は `time_entries.google_event_id` で紐づく**

- 予定ブロックからタイマーを開始すると、その予定の `google_event_id` を持つ実績ができる
  → オーバーレイで横並びに表示され、ズレ(遅れ・超過)が計算できる
- `google_event_id IS NULL` の実績 = フリータイマー / 割り込み作業(オーバーレイでは柿色+「フリー」ラベル)

**(3) 「実行中タイマーは常に1本」はDBが保証する**

- `end_at IS NULL` の行 = 実行中タイマー
- partial unique index `one_running_timer_per_user`(`(user_id) WHERE end_at IS NULL`)により、
  アプリ側のバグや複数デバイスの競合があっても2本目は挿入できない。
  アプリ側チェックはUXのためで、**最終防衛線はDB制約**

### RLSの規約(詳細は [P0-6](specs/P0-6_DBスキーマとRLS.md)、`db-migration` Skill)

- 全テーブルRLS有効。ポリシーは `user_id = (select auth.uid())` の own 4種(select/insert/update/delete)が基本形。
  **`to authenticated` を明示する**(P6-2)— 未認証リクエストでポリシー評価自体をスキップできる
- **`google_tokens` と `pro_interest_events` はRLS有効だがポリシーを一切作らない**
  = anon/authenticated からは何もできず、service role のみアクセス可能
- ヘルパー関数(`handle_new_user`, `set_updated_at`)は `private` スキーマに
  `SECURITY DEFINER` + `set search_path = ''` で作成
- **テーブルを追加したら `authenticated` への `grant` をマイグレーションに明示する**(P6-5)。
  既定権限を止めたため自動では付かない。付け忘れるとPostgRESTから権限エラーになる

**三重防御**: RLS有効 + ポリシーゼロ/最小 + GRANT最小化。どれか1つが破れても他が止める。

## 7. 主要データフロー

### 7.1 タイマー開始/停止(楽観的更新 + DB制約)

```mermaid
sequenceDiagram
    participant UI as calendar-view.tsx / track-view.tsx<br/>(Client)
    participant SA as timer-actions.ts<br/>(Server Action)
    participant SVC as lib/timer/service.ts
    participant DB as Postgres (RLS)

    UI->>UI: 楽観的更新 (setRunning に仮の実行中状態)
    UI->>SA: startTimerAction(title, googleEventId?)
    SA->>SA: getSessionUser() で認証確認
    SA->>SVC: startTimer()
    SVC->>DB: 既存の実行中 (end_at IS NULL) を停止
    SVC->>DB: insert (start_at = サーバー時刻)
    Note over DB: partial unique index が最終防衛線。<br/>別デバイス競合 (23505) は1回だけリトライ
    SA->>SA: revalidatePath("/calendar", "/track")
    SA-->>UI: 成功
    UI->>UI: router.refresh() でサーバー状態と同期
    Note over UI: 失敗時は setRunning(previous) でロールバックし<br/>日本語エラーメッセージを表示
```

ポイント:

- **時刻は常にサーバーが決める**(クライアントの時計を信用しない)
- 別タイマー実行中に別の予定をタップしたら、**エラーにせず既存を自動停止して新規開始**
- 停止は冪等(すでに止まっていても正常終了)
- 実行中エントリの編集・削除は不可。`updateTimeEntry` / `deleteTimeEntry` は
  `.not("end_at", "is", null)` ガードで確定済みのみを対象にする
  (実行中は開始時刻変更 `updateRunningStart` のみ可)
- 経過時間表示(1秒更新)はクライアント側の `lib/timer/use-now-seconds.ts` が担当。
  ポーリングはせず、リロードや複数デバイスでもDBの実行中行から復元される

### 7.2 Googleカレンダー同期(凍結中。フラグONで動作)

```mermaid
sequenceDiagram
    participant CV as calendar-view.tsx (Client)
    participant RH as POST /api/calendar/sync<br/>(Route Handler)
    participant Admin as lib/supabase/admin.ts<br/>(service role)
    participant G as Google (OAuth / Calendar API)
    participant DB as Postgres (RLSクライアント)

    CV->>RH: マウント時・表示週変更・手動更新で fetch<br/>(body = computeSyncRange: 表示週±1週間)
    RH->>RH: GOOGLE_INTEGRATION_ENABLED 確認 (OFFなら404)
    RH->>RH: auth.getUser() / 範囲上限35日チェック
    RH->>Admin: getGoogleRefreshToken()
    Admin-->>RH: refresh_token (無ければ 401 not_connected)
    RH->>G: refreshAccessToken()
    Note over RH,G: invalid_grant なら失効トークンを削除して<br/>401 reauthorize (再認可導線へ)
    RH->>G: fetchPrimaryEvents() (primaryのみ・終日イベント除外)
```

ポイント:

- 同期は**オンデマンドのみ**(webhook / push channel なし)。
  UXは「キャッシュ表示先行 → バックグラウンド同期 → 反映」
- **権限の使い分けが肝**: `google_tokens` の読み書きは service role、
  `synced_events` の読み書きは**ユーザー自身のRLSクライアント**。
  Google API呼び出しはこのRoute Handlerに集約されている
- Google連携の認可は Supabase Auth の `signInWithOAuth` を**使わない**独自OAuth2コードフロー
  (`/api/google/connect` → Google → `/api/google/callback`、state cookieでCSRF対策)。
  `signInWithOAuth` だとセッションが別アカウントに切り替わる危険があるため([P1-3](specs/P1-3_メール認証とGoogle任意連携.md))

### 7.3 定期予定のオンデマンド実体化

`recurring_rules` はルール(「毎週火木 9:00-10:00」等)だけを持ち、カレンダーに並ぶ実体は
**ページ表示のたびに `synced_events` へ冪等生成**される。

```mermaid
sequenceDiagram
    participant Page as calendar/track/summary の page.tsx<br/>(Server Component)
    participant Rec as lib/calendar/recurring.ts
    participant DB as Postgres

    Page->>Rec: materializeRecurringInstances(supabase, baseDate)
    Rec->>DB: recurring_rules + recurring_exceptions を取得
    Rec->>Rec: expandOccurrences: 表示範囲にルールを展開<br/>(ローカル時刻+IANA TZ → UTC変換、例外日を除外)
    Rec->>DB: synced_events へ insert<br/>(google_event_id = "rec:ルールID:日付", ignoreDuplicates)
    Page->>DB: fetchSyncedEvents() (実体化の後に直列実行)
    Page-->>Page: props で CalendarView へ
```

この設計の狙い: 実体化さえ済めば、**タイマー・オーバーレイ・サマリーの既存ロジックは
一切変更せずに定期予定へ対応できる**。「この回のみ削除」は `recurring_exceptions` に tombstone を積み、
「繰り返し全体の削除」でも過去のインスタンスは残す(計画した事実を保持する)。

### 7.4 実績からの予定提案([P5-2](specs/P5-2_実績からの予定提案.md) / [P5-7](specs/P5-7_平日毎日まとめ提案.md))

DBテーブルの追加なし。純粋関数 `computeSuggestions`(`lib/calendar/suggestions.ts`)で完結する:

1. ページが直近4週間の完了実績を取得し、propsで `plan-suggestions.tsx` へ
2. クライアントで「同タイトル × 同曜日 × 開始時刻差60分以内」のクラスタを検出(2日以上発生したもののみ)
3. 開始時刻・所要時間の**中央値**を15分単位に丸めて提案(最大3件)。
   既存予定・定期ルールと重複するもの、過去日時は除外
4. 受け入れは「この週に追加」(単発予定)/「毎週にする」(定期ルール化)
   — どちらも既存のServer Actionを再利用

### 7.5 提案経由の定期予定の学習補正([P10-1](specs/P10-1_提案経由予定の学習補正.md))

「毎週にする」で受け入れた定期予定(`origin='suggestion'`)を、**実績の中央値に合わせて自動調整**する。
P5-2 と同じ「中央値 → 15分丸め」の哲学を踏襲している。

```mermaid
sequenceDiagram
    participant Page as calendar/page.tsx<br/>(Server Component)
    participant RL as lib/calendar/rule-learning.ts
    participant Rec as lib/calendar/recurring.ts
    participant DB as Postgres

    Page->>Page: origin='suggestion' のルールが0件なら丸ごとスキップ
    Page->>DB: fetchRuleLearningEntries (直近42日の実績)
    Page->>RL: computeRuleAdjustments(rules, entries, now)  ※純粋関数
    Note over RL: 最低3サンプル・7日おき再学習・<br/>15分未満の差は無視
    RL-->>Page: RuleAdjustment[]
    Page->>RL: applyRuleAdjustments → recurring_rules を UPDATE
    Page->>Rec: 調整があったときだけ再実体化<br/>(今日以降を新しい値で作り直す)
    Page-->>Page: ruleAdjustments を props で渡し<br/>RuleAdjustmentBanner が通知
```

**実装上の落とし穴が1つ**(`app/(app)/calendar/page.tsx:96-98` のコメント):
Next.js の fetch リクエストメモ化により、`recurring_rules` へ**同一レンダー内で同じSELECTを再度投げても
更新前の内容が返る**。そのため再実体化ではDBを読み直さず、既知のルール一覧に調整結果を
マージした値を明示的に渡している。

## 8. 時刻とタイムゾーンの扱い

**このプロジェクトで最も事故が起きやすい領域**。実装前に必ず読むこと。

### 大原則

1. **DBには常にUTCで保存し、表示時にユーザーのタイムゾーンへ変換する**
2. **`Date` の直接演算を避け、date-fns / `@date-fns/tz` を使う**
3. **開発機は JST、CI(GitHub Actions)は UTC** — ローカルで通ってもCIで落ちる

### 問題の構造: サーバーは訪問者のTZを知らない

Server Component は Vercel 上で **UTC** として動く。一方ブラウザはユーザーのTZ。
そのまま `new Date()` で「今日」を判定すると、サーバーとクライアントで日付がずれる。

これを解決するのが **TZ Cookie の往復**([P8-3](specs/P8-3_サマリーの日付またぎとTZ非対称の是正.md)):

```mermaid
sequenceDiagram
    participant B as ブラウザ
    participant TS as components/timezone-sync.tsx
    participant SC as Server Component<br/>(summary/page.tsx など)

    B->>SC: 初回リクエスト (Cookieなし)
    SC->>SC: readTimezoneCookie() → null<br/>→ サーバーTZで概算して描画
    SC-->>B: HTML
    B->>TS: マウント
    TS->>TS: Intl.DateTimeFormat().resolvedOptions().timeZone
    Note over TS: 既存Cookieと同値なら何もしない<br/>(毎回書くとrefreshループになる)
    TS->>B: document.cookie に plandiff-tz を書く
    TS->>SC: router.refresh()
    SC->>SC: readTimezoneCookie() → "Asia/Tokyo"<br/>resolveNowInTimezone() で訪問者TZの「今」を作る
    SC-->>B: 正しい日付境界で再描画
```

関連ファイル:

| ファイル | 役割 |
|---|---|
| `lib/time/timezone-cookie.ts` | Cookie名と値の形式検証。**`next/headers` を持ち込まない**(クライアントからもimportするため) |
| `lib/time/timezone-cookie.server.ts` | Cookie読み取り(`next/headers` 依存のため分離) |
| `lib/time/now-in-timezone.ts` | `TZDate` で「訪問者TZでの現在時刻」を組み立てる。不正なTZ名は例外にせず base へフォールバック(不正Cookieでも SSR を落とさない) |
| `components/timezone-sync.tsx` | 上図のクライアント側。`app/(app)/layout.tsx` に1つだけ配置 |

### ハイドレーション不整合の回避

「今日」の判定や現在時刻線をSSRで描くとハイドレーションエラーになる。
そこで **`useSyncExternalStore` のサーバースナップショットを `null` にする**パターンを使う
(`lib/time/use-now-minute.ts`, `lib/timer/use-now-seconds.ts`)。
SSR時は `null` が返るので何も描画されず、ハイドレーション後にのみ時刻依存のUIが現れる。

### 日付またぎへの追従([P8-1](specs/P8-1_日付またぎの自動反映.md) 〜 P8-3)

`lib/time/use-now-minute.ts` が分単位の共有ストアを提供する。設計上の要点:

- **ストアはモジュールスコープに1つ**(購読コンポーネントごとにタイマーを張らない)
- **分境界にアラインした `setTimeout` 連鎖**で駆動する
  — 固定間隔の `setInterval` だと0時の検知が最大60秒遅れる
- `visibilitychange` / `focus` / `pageshow` でも再計算する
  — バックグラウンドタブのタイマースロットリングと、PWAのプロセスサスペンドからの復帰に対応
- 秒精度が要る実行中タイマーは `useNowSeconds` を使い続ける

### R-1: 日時テストはローカルTZで組み立て、`TZ=UTC` で確認する

**同じバグを3回出したためルール化された**(CLAUDE.md「バグ由来ルール」)。

- テストデータの日時は **`new Date(2026, 6, 7, 9, 0)` のようにローカルTZで構築する**。
  `"2026-08-03T00:00:00Z"` や `"+09:00"` 付きのISO文字列で固定しない
  (`startOfDay` はローカルTZで動くため、UTCとJSTで日の境界がずれる)
- 「今日」に依存するテストは基準時刻を固定する
  (`vi.useFakeTimers({ shouldAdvanceTime: true })` + `setSystemTime` で正午など)
- **日時が絡むテストを追加・変更したら、コミット前に `TZ=UTC npx vitest run <file>` を実行する**。
  境界値を触った場合は `TZ=Pacific/Kiritimati`(UTC+14)も確認すると西→東の両方向を潰せる
- pre-commit フックはローカルTZで走るため、この確認を代替しない

### デザイントークンと raw color 禁止

変更時は必ず両方を揃える**。

この規約は **テストで強制されている**: `tests/lib/design/no-raw-colors.test.ts` が
`app/**/*.tsx` と `components/**/*.tsx` を走査し、`bg-blue-500` のような直書きカラークラスと
`dark:` バリアントを検出したら失敗する。

### 即時フィードバック([P12-1](specs/P12-1_カレンダー操作の即時フィードバック.md))

`page.tsx` のサーバー往復が重いため、ナビゲーション操作で「クリックしても数秒反応しない」問題があった。
`useTransition` を1本(`viewPending`)導入し、共通ヘルパー `startViewUpdate` 経由で
`router.push` / `router.refresh` を12箇所ラップしている。

**設計上の要点**: `router.push` / `refresh` は `void` を返すため、素の `startTransition` では
`isPending` が即座に false へ戻る。`startTransition(async () => { await update() })` と
**非同期トランジションにすることで RSC 再取得のコミットまで pending を保てる**。

UI表現はナビ系ボタンの `disabled:opacity-50`、日付ラベル横の `Loader2` + `role="status"`、
グリッドの `aria-busy` + `pointer-events-none opacity-60`。
タイマー系(既に楽観的更新済み)は対象外。

### 守るべき不変条件

**集計規則は `computeGapSummary` と `computeDailyGapSeries` で完全に一致させる**
— 「開始時刻が期間内にあるものだけを、その開始日に全量計上する」。
これにより**グラフの系列の総和がヒーローの集計値と必ず一致する**。
この不変条件は `chart.ts` のテスト S10 で固定されている。

範囲をまたぐ予定・実績は集計対象外(仕様。[P3-2](specs/P3-2_ギャップサマリー.md))。

### 行数上限のバグと対策([P6-0](specs/P6-0_サマリー集計の行数上限.md))

PostgREST には1レスポンスあたりの行数上限(`max_rows`、Supabaseの既定は1000)があり、
**上限に達すると*エラーなく*打ち切られる**。`.limit()` を付けていないクエリでも同じで、
サマリーの長期間表示(最大366日)では集計値が黙って過小になっていた。

対策は `lib/supabase/paged-fetch.ts`:

- `.range()` でページを繰り返し取得して全件を組み立てる(`PAGE_SIZE = 1000`)
- **想定を超えたら部分結果を返さず `RowLimitExceededError` で明示的に失敗させる**
  (`MAX_FETCH_ROWS = 20000`)。黙って打ち切ることが本バグの原因だったため

「エラーを握りつぶさず、正しく失敗させる」というこのプロジェクトの姿勢が最もよく出ている実装。

### P6-3 で意図的に見送ったもの

仕様書 3-D は最終ステップに `useCallback` + `React.memo` を計画していたが、**実装時に見送られた**。
理由は「依存の連鎖が `calendar-view.tsx` 全体に及び、stale closure のリスクが効果に見合わない」。
重い計算(`layoutDayEvents` × 2、`computeActualGaps`)は `DayColumn` 内の `useMemo` で既に止まっているため、
`React.memo` の追加分は限界効用が小さいと判断された。

同様に `now` の `useMemo` 固定も取りやめている
(現在時刻ラインがハイドレーション時刻で永久固定になるため)。代わりに `actualInputs` の基準時刻を
**分単位に丸めて参照を安定させる**方法を採った(`calendar-view.tsx:802-813`)。
この「分単位に丸める」発想が後に P8-1 の `use-now-minute.ts` へつながっている。

### P6-2 の `span` 生成列に潜む2つの罠

マイグレーションのコメントが秀逸なので、要点だけ引く:

```sql
case
  when start_at = end_at then tstzrange(start_at, end_at, '[]')  -- 罠1
  when start_at < end_at then tstzrange(start_at, end_at, '[)')
  else null                                                       -- 罠2
end
```

1. **`[x,x)` は空範囲で、何とも重ならない**。ゼロ長の行は作りうる(タイマーの即時停止、Google側の予定)ため、
   `case` がないとゼロ長の予定・実績が一覧から**黙って消える**
2. **生成列の評価は CHECK 制約より先に走る**。`end_at < start_at` を `tstzrange()` へ渡すと
   `data_exception`(22000)が上がり、本来の `check_violation`(23514)を覆い隠す。
   不正データの拒否は CHECK に任せ、生成列は `null` へ倒す

`time_entries` では `end_at IS NULL`(実行中)が `tstzrange(start_at, null, '[)')` = 上端非有界となり、
「まだ終わっていない」という意味とちょうど一致する。

### P6-5 が示す姿勢

発見時点で「どの経路からも悪用できない」ことは確認されていた
(RLSがポリシーゼロで全拒否、PostgRESTはTRUNCATE非公開、`anon` にDBログインなし)。
それでも直したのは、**防御が一段減っていることと、既定権限で新規テーブルにも自動付与されるため**。
この判断基準は今後も踏襲する。

### スコープ外として記録されている項目

`docs/開発計画.md` の「Phase 6 のスコープ外」に、見送った理由つきで記録されている
(認証4ページの `supabase-js` 削減、`calendar-view.tsx` の分割、`getClaims()` 移行、
サマリー集計のRPC化、`recurring_rule_id` の正規化)。
**同じ検討を繰り返さないため、着手前にここを読むこと。**

## 12. 初学者がつまずくポイント

1. **「Googleカレンダーと同期されない」— 仕様です(凍結中)**。
   `GOOGLE_INTEGRATION_ENABLED` が未設定/false のとき、同期API・連携UIはすべて404/非表示になる。
   ローカルで連携を試すにはフラグONとGoogle OAuthクレデンシャルが必要
2. **日時はすべてUTCでDB保存、表示時にユーザーTZへ変換**。§8 を必ず読む。
   過去に `TZDate` のコピーコンストラクタがTZを引き継がずCI(UTC環境)でだけ落ちるバグがあった
   (2026-07-15ログ)
3. **SSRとクライアントのTZ不一致**: サーバーはUTC、ブラウザはユーザーTZ。
   `useSyncExternalStore` のサーバースナップショットを `null` にしてハイドレーション後にのみ描画する(§8)
4. **`server-only` の import 規約**: サーバー専用モジュール(`lib/supabase/admin.ts`、`lib/google/token.ts`、
   `lib/calendar/rule-learning.ts`、`lib/supabase/paged-fetch.ts` 等)は冒頭で `import "server-only"`。
   クライアントからも使う純粋関数(`sync-range.ts`, `suggestions.ts`, `layout.ts`, `gap.ts`, `view-date.ts` 等)には**付けない**。
   テストでは `tests/stubs/server-only.ts` で空スタブ化している
5. **文言は `lib/**/messages.ts` に集約**(日本語)。UIテキストをコンポーネントにハードコードしない
6. **色をハードコードしない**。`tests/lib/design/no-raw-colors.test.ts` が失敗する(§9)
7. **Next.js の fetch メモ化**: 同一レンダー内で同じSELECTを再度投げても更新前の内容が返る。
   更新直後に読み直す設計にしない(§7.5 の実例)
8. **非同期トランジションのテストは未解決Promiseを残さない**。
   残すと次のテストを汚染する(P12-1 の実装時に判明)。各テスト末尾で `deferred.resolve()` する
9. **Next.js 16 は学習データと違う可能性がある**。`AGENTS.md` の指示どおり、
   `node_modules/next/dist/docs/` のガイドを読んでから書くこと(例: middleware → `proxy.ts`)

## 14. やってはいけないこと

- Googleのトークン・APIキーをクライアントバンドル・ログ・エラーメッセージに含める
- RLSなしのテーブルを作る / `anon` キーで `google_tokens` にアクセスする
- **テーブルを追加して `authenticated` への `grant` を書き忘れる**(既定権限を止めているため自動では付かない)
- Google Calendar の **write スコープを追加するPRを出す**(OAuth審査要件が変わる。人間が判断する)
- カレンダーデータを表示・ギャップ分析以外の目的で保存・加工する(Google Limited Use 要件)。
  設定画面の「データ全削除」はこの要件への対応でもある
- マイグレーションを経ないスキーマ変更(Supabaseダッシュボードの直編集)
- MVPスコープ外(書き戻し、複数カレンダー、レポート出力、課金実装)を先回りで作る
- **テストの無効化・削除によってテストを「通す」**
