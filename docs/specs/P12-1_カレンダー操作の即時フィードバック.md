## 目的

カレンダー画面(`/calendar`)のナビゲーション系ボタン(週表示の日ヘッダー・日表示の
`WeekStrip`・週送りprev/next・今日・表示切替)と、予定/実績の保存・削除ボタンについて、
クリック直後に視覚的なフィードバック(disabled化・スピナー・グリッドの一時的な減光)を
表示し、「押しても反応していないように見える」体感を解消する。

### 原因

`app/(app)/calendar/page.tsx` は Server Component で、プロフィール取得・繰り返し予定の
実体化・ルール学習補正・Google トークン確認・イベント/実績取得を毎回まとめて行う重い処理を
持つ。`components/calendar-view.tsx` の対象ボタンは `router.push()` または `router.refresh()`
を呼んでこの `page.tsx` を丸ごと再実行させるが、`useTransition` でラップされていないため
`isPending` に相当する信号が一切なく、クリックしても即座には何も変化しない。さらに
`buildCalendarPath`(`lib/calendar/view-date.ts`)は同一ルート(`/calendar`)へのクエリ
パラメータ変更のみのため、既存の `app/(app)/loading.tsx` はこの遷移では発火しない。結果として
サーバー往復(数秒)が完了するまで画面が固まって見える。

実処理時間そのもの(週またぎ時のGoogle同期→`router.refresh()`の二重往復、`page.tsx`の処理
コスト)の短縮は、既存のP6-4(凍結解除待ち)が対応する範囲であり、**本仕様のスコープ外**とする。
本件はユーザーが選択した方針(即時フィードバックの追加を優先)に基づく。

## 仕様

### 方針(plan modeでユーザー承認済み)

`components/calendar-view.tsx` に `useTransition` を1本だけ導入し、対象の
`router.push`/`router.refresh` 呼び出しをラップして得られる `isPending` を、
「カレンダー表示がサーバー最新状態に追いつくまで」を表す単一のフラグ `viewPending` として
UIに反映する。

```ts
const [viewPending, startViewTransition] = useTransition();
```

既存の `eventPending`/`editPending`(Server Action 呼び出し中のパネル制御専用)とは役割を
分離し、変更しない。

### 変更内容: `components/calendar-view.tsx`

**`startViewTransition` でラップする箇所**(`router.push`/`router.refresh` 呼び出しを
`startViewTransition(() => ...)` で包む):

1. `handleNavigate`(303-313行、週送りprev/next)
2. `handleToday`(314-316行)
3. `handleViewChange`(317-321行、表示切替)
4. 週表示ヘッダーの `onClick`(937-939行)
5. `WeekStrip` の `onSelect` 呼び出し元(913-915行)
6. `handleSaveEvent`(581-591行)・`handleDeleteEvent`(604-614行)・
   `handleSaveRecurringRule`(624-634行)・`handleSaveRuleEdit`(658-667行)・
   `handleDeleteRule`(676-686行)・`handleSaveEdit`(741-751行)・
   `handleDeleteEditing`(760-770行): 各 `.then` 内、成功時の `router.refresh()` のみを
   ラップする。`setEventPanel(null)`/`setEditingEntry(null)` は現状どおり `refresh` より
   先に同期実行し、パネルは即座に閉じる(「入力操作は受理された」ことを即時に伝える)

**対象外(変更しない)**:

- タイマー系(`startTimerOptimistic`・`handleStopTimer`、340-404行)の `router.refresh()`:
  既に自前の楽観的更新(`setRunning`)で即時反応済みのため、`viewPending` を混ぜると
  グリッドが不要に減光し即時感を損なう
- `handleSaveStart`(実行中タイマーの開始時刻編集、448-465行)の `router.refresh()`:
  本仕様の対象範囲外
- 同期 `useEffect`(218-268行)・日付またぎ `useEffect`(275-289行)の `router.refresh()`:
  ユーザーのクリック起点ではない自動更新のため対象外

**`WeekStrip` コンポーネントの変更**(1144行〜):

- props に `pending: boolean` を追加
- 各日ボタンに `disabled={pending}` を追加
- 呼び出し元(909-917行)から `pending={viewPending}` を渡す

**ナビゲーション系ボタンのUI変更**:

- prev/今日/next(807-829行)、表示切替 day/week(841-853行)、週表示ヘッダーの各日ボタン
  (930-953行)に `disabled={viewPending}` を追加。クラス文字列に既存の `disabled:opacity-50`
  トークンを足す
- 日付ラベル(831-833行 `<p>{rangeLabel}</p>`)の隣に、`viewPending` の間だけ
  `lucide-react` の `Loader2`(`className="h-3.5 w-3.5 animate-spin motion-reduce:animate-none"`、
  `aria-hidden="true"`)を表示する
- 上記スピナーと併せて、`role="status" aria-live="polite"` を持つ `sr-only` のテキストを
  `viewPending` の間だけ描画し、スクリーンリーダーに状態を伝える。文言は
  `CALENDAR_MESSAGES.viewUpdatingLabel`(新規、後述)を使う

**グリッド本体のUI変更**(`scrollRef` を持つコンテナ、919行〜):

- `aria-busy={viewPending}` を付与する
- `viewPending` の間、`pointer-events-none opacity-60 transition-opacity duration-150` を
  クラスに追加する(古いデータへの誤操作防止と、視覚的な「更新中」表現を兼ねる)

**予定/実績の保存・削除パネル**:

- パネルは成功時に即座に閉じる(現状どおり)。閉じた後の「グリッドがまだ古いまま」は、
  上記グリッドの減光+スピナーがそのまま「反映待ち」を表すため、新規のオーバーレイ
  コンポーネントは作らない

### 変更内容: `lib/calendar/messages.ts`

新規キーを1つ追加する(既存の `syncing` はGoogle同期専用の文言のため流用しない):

```ts
viewUpdatingLabel: "表示を更新しています",
```

## スコープ外

- 実処理時間そのものの短縮(週またぎ時のGoogle同期→`router.refresh()`の二重往復の解消、
  `page.tsx`の処理コスト見直し)。既存のP6-4(凍結解除待ち)が対応する範囲とする
- タイマー開始/停止ボタンの変更(既に楽観的更新済みで対象外)
- 実行中タイマーの開始時刻編集(`handleSaveStart`)への `viewPending` 適用
- カレンダーグリッド全体を覆う半透明スクリムオーバーレイの新設(z-index競合・375px崩れの
  リスクがあるため、グリッドコンテナの減光のみで対応する)

## テストシナリオ

対象ファイル: 既存の `tests/components/calendar-view*.test.tsx` 群に追記する
(新規ファイルは作らない。`viewPending` は既存コンポーネントの横断的な振る舞い変更のため)。

モック済み `useRouter`(`push`/`refresh` が同期 `vi.fn()`)は実際のRSCフェッチの
サスペンドを再現できないため、`fireEvent.click` 直後(同期)の時点での状態検証と、
`router.push`/`refresh` のモック実装を意図的に遅延させた上での `waitFor` による
「反映後に元へ戻る」検証を分けてシナリオ化する。

### `tests/components/calendar-view.test.tsx`(prev/next/today/表示切替)

- S1 [単体]: Given カレンダー画面を表示中 When 「次へ」ボタンをクリック Then クリック直後に
  「前へ」「今日」「次へ」「日」「週」の各ボタンが `disabled` になる
- S2 [単体]: Given S1の状態(`router.push` が未解決) When `router.push` のモックが解決する
  Then 各ボタンの `disabled` が解除される
- S3 [単体]: Given カレンダー画面を表示中 When 表示切替の「週」ボタンをクリック Then
  クリック直後に `viewUpdatingLabel` のテキストを持つ `role="status"` 要素が現れる

### `tests/components/calendar-view-week-select.test.tsx`(週ヘッダー・WeekStrip)

- S4 [単体]: Given 週表示 When 今日以外の曜日ヘッダーをクリック Then クリック直後に
  すべての曜日ヘッダーボタンが `disabled` になる
- S5 [単体]: Given 日表示 When `WeekStrip` の曜日ボタンをクリック Then クリック直後に
  `WeekStrip` の全ボタンが `disabled` になる(`pending` propの伝播確認)
- S6 [単体・境界値]: Given S4の状態(`disabled` 中) When 同じ曜日ヘッダーを再度クリックしようと
  する Then `router.push` が追加で呼ばれない(`disabled`によるクリック無効化の確認)

### `tests/components/calendar-view-app-events.test.tsx`(予定の作成・編集・削除)

- S7 [結合]: Given 予定作成パネルを開き入力済み When 保存ボタンをクリックして
  Server Actionが成功する Then パネルは即座に閉じ、その直後(`router.refresh`未解決の間)
  グリッドコンテナに `aria-busy="true"` が付いている
- S8 [結合]: Given S7の状態 When `router.refresh` のモックが解決する Then グリッドコンテナの
  `aria-busy` が `false` に戻る
- S9 [異常系・単体]: Given 予定作成パネルを開き入力済み When 保存のServer Actionが失敗する
  (`result.ok: false`) Then `router.refresh` は呼ばれず、`viewPending` に由来する
  `aria-busy` も立たない(既存の `eventError` 表示のみが機能する)
- S10 [結合]: 予定削除ボタンでも S7 と同様の一連の流れになることを確認する

### `tests/components/calendar-view-recurring.test.tsx`(繰り返し予定)
