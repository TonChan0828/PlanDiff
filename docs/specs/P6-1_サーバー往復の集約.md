# 仕様書: サーバー往復の集約(P6-1)

- ステータス: ドラフト
- 関連: docs/開発計画.md Phase 6 / docs/specs/P5-1_定期予定.md(実体化) / docs/specs/P5-9_サマリーの任意期間表示.md
- 指示資料: なし(`docs/指示資料/` を確認。関連資料なし)

## 目的

全ページの TTFB を縮める。現状、1 リクエストの中で**同じ情報を何度も Supabase に問い合わせている**。

`supabase.auth.getUser()` は毎回 `GET /auth/v1/user` への HTTP 往復であり、ローカルキャッシュはない。
`/calendar` を 1 回開くと、次の 4 箇所で**直列に** 4 往復する。

| # | 箇所 |
|---|---|
| 1 | `proxy.ts:35` |
| 2 | `app/(app)/layout.tsx:20` |
| 3 | `app/(app)/calendar/page.tsx:47` |
| 4 | `lib/calendar/recurring.ts:500`(`materializeRecurringInstances` 内) |

`/track` も 4 回、`/summary` 3 回、`/settings` 3 回。
Server Action は action 側と lib 側で 2 回ずつ(`timer-actions.ts` 5 本 + `event-actions.ts` 7 本 = 12 アクション)。

さらに、RSC ではレイアウトの `await` が解決するまで children のレンダーが始まらないため、
これらは並列化されずそのまま TTFB に積み上がる。

## 検証済みの前提(実装方式の根拠)

**React 19.2.4 の `cache()` は、リクエストコンテキスト外では素通しする**(メモ化せず、例外も投げない)。
実測で確認した:

```
react version: 19.2.4
typeof React.cache: function
calls: 2 | same ref: false
RESULT: PASSTHROUGH (no memoization outside request context)
```

ここから 2 つの帰結がある。

1. `cache()` を導入しても **既存 528 件のテストは壊れない**(vitest では素通しになるだけ)
2. **逆に、vitest では `cache()` による重複排除を検証できない**。
   「1 リクエストで `getUser` が 1 回」を単体テストで固定できない

(2) は当初計画の弱点なので、**重複排除は `cache()` に依存させない**設計にする(下記)。

## 仕様

### 1-A: `getSessionUser` を WeakMap でクライアント単位にメモ化する

`lib/supabase/server.ts` に次を追加する。

```ts
import { cache } from "react";

// 1 リクエスト内で同一インスタンスを共有する(cookie ストアの読み取りも 1 回で済む)
export const createClient = cache(async () => { /* 既存の実装のまま */ });

// クライアントインスタンス単位に getUser の結果(Promise)を保持する。
// createClient が cache 済みなので 1 リクエスト = 1 インスタンス = 1 往復に収束する。
const userByClient = new WeakMap<SupabaseClient, Promise<User | null>>();

export function getSessionUser(client: SupabaseClient): Promise<User | null> {
  const cached = userByClient.get(client);
  if (cached) return cached;
  const promise = client.auth
    .getUser()
    .then(({ data }) => data.user ?? null);
  userByClient.set(client, promise);
  return promise;
}
```

**なぜ `cache()` 単独にしないか**:
`cache()` はリクエストコンテキストの外で素通しするため、vitest で挙動を固定できない。
WeakMap によるインスタンス単位のメモ化なら **RSC・Server Action・Route Handler・vitest のすべてで同じ挙動**になり、
「同じ client なら 1 回」を単体テストで検証できる。

**なぜモジュールスコープの WeakMap が安全か**:
キーがクライアントインスタンスであり、インスタンスはリクエストごとに新しく作られる。
ユーザーをまたいで共有されることはなく、リクエスト終了後は GC 対象になる。
(`createClient` を `cache()` で包むのは、同一リクエスト内でインスタンスを共有させるため)

**Promise を保存する理由**: 解決値ではなく Promise を保存することで、
同一リクエスト内の並行呼び出し(`Promise.all` の中など)でも往復が 1 回に収まる。

### 1-A-2: 呼び出し側の置換

`client.auth.getUser()` を直接呼んでいる 37 箇所のうち、**client を引数で受け取る lib/ と、
`createClient()` の結果を使う app/ の呼び出し**を `getSessionUser(client)` に置換する。

- `lib/timer/service.ts`(4 箇所)
- `lib/calendar/app-events.ts`(3 箇所)
- `lib/calendar/recurring.ts`(5 箇所)
- `app/(app)/**/*.ts(x)`(layout / 各 page / 各 action)
- `app/api/**`(Route Handler。1 リクエスト 1 回のため効果はないが、書き方を揃える)

**`proxy.ts` は置換しない**。Proxy は別インスタンスを自前で作っており、
セッション cookie の更新という別の役割を持つ。ここを触ると認証の挙動に影響するため対象外。

**既存の DI(テストがモッククライアントを注入する設計)は維持する**。
引数なし版にすると lib/ が内部で本物の `createClient()` を呼んでしまい、既存テストが壊れる。

### 1-B: 直列ウォーターフォールの解消

**`app/(app)/calendar/page.tsx`**: 現在 `getUser` → `profiles`(オンボ判定) → `materializeRecurringInstances`
→ `Promise.all` の 3 段直列。`profiles` の取得を `materializeRecurringInstances` と並列化し、
`shouldRedirectToOnboarding` の判定は両方の解決後に行う。

- `materializeRecurringInstances` は `fetchSyncedEvents` の前に完了必須(P5-1 の仕様)なので、
  `Promise.all` の前という位置関係は変えない
- `redirect()` はレンダー前に呼べば安全。ただし `redirect` は例外を投げるため、
  **`Promise.all` の中では呼ばない**(未処理の rejection になる)。解決後に判定する

**`app/(app)/settings/page.tsx`**: `getUser` → `await searchParams` → `getGoogleRefreshToken` の
3 段直列を `Promise.all([getSessionUser(...), searchParams])` に畳む。

### 1-C: `materializeRecurringInstances` の軽量化

`lib/calendar/recurring.ts:495-583` は GET のたびに
`getUser` → `recurring_rules` select → `recurring_exceptions` select → `upsert` の 4 往復を直列実行する。

1. `getUser` は 1-A で往復ゼロになる
2. **`recurring_exceptions` の select に期間フィルタを追加する**。
   現在は `.in("rule_id", ruleIds)` のみで**全期間**の例外を取っている。
   `.gte("occurrence_date", ...)` / `.lt("occurrence_date", ...)` を追加すれば
   UNIQUE `(rule_id, occurrence_date)` インデックスが効き、ルールが古いほど効果が出る。
   境界は実体化する範囲(`range.timeMin` / `range.timeMax`)のローカル日付に合わせる。
   **タイムゾーン差で端の例外を取りこぼさないよう、前後 1 日のバッファを取る**
3. **`/calendar` の `recurring_rules` 二重取得を解消する**。
   `materializeRecurringInstances`(`:505`)と `fetchRecurringRules`(`:463`)は
   同一テーブル・同一カラム集合を 1 リクエストで 2 回 select している。
   `materializeRecurringInstances` の戻り値を `RecurringRuleSummary[]` に変え、
   `calendar/page.tsx` の `Promise.all` から `fetchRecurringRules` を外す。
   `fetchRecurringRules` 自体は削除しない(`/track` `/summary` は戻り値を使わないため無改修)

### 1-D: 軽微な改善

- `lib/supabase/admin.ts:7` の `createAdminClient()` を、モジュールスコープの lazy singleton にする
  (現在は `getGoogleRefreshToken` ほか各関数の中で毎回インスタンスを生成している)。
  環境変数が未設定なら従来どおり例外を投げる挙動を保つ
- `proxy.ts:41` の matcher から `(marketing)` の静的ページを除外する。
  現在は LP・料金・プライバシー・利用規約でも毎回 Supabase Auth に 1 往復してから配信される。
  除外対象: `/`(LP) / `/pricing` / `/privacy` / `/terms`。
  **認証が絡むページ(`/login` `/signup` `/reset-password` `/forgot-password`)は除外しない**

## スコープ外

- **`getClaims()`(ローカル JWT 検証)への移行**。Supabase の非対称 JWT 署名キー有効化(ダッシュボード作業)が
  前提であり、P6-1 で往復が 1 回に減った後に「その 1 回も消す」施策として別途評価する
- **`proxy.ts` の `getUser()` 自体の削除**。セッション更新という別の役割があるため触らない
- **`materializeRecurringInstances` を読み取りパスから外すこと**。P5-1 のオンデマンド実体化という
  設計判断そのものの変更になるため、今回は「同じ設計のまま軽くする」に留める
- **DB インデックスの追加**。P6-2 で扱う
