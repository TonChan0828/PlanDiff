# 仕様書: G-108 定期予定の編集と関連データの更新を一つのトランザクションにする

- ステータス: 承認済み(2026-11-24)
- 関連: GitHub Issue #108(優先度P1・不具合) / [P5-1 定期予定](P5-1_定期予定.md) / `supabase/migrations/20260930104908_atomic_timer_operations.sql`(同じ方式の先例)
- 指示資料: なし(2026-11-24 に `docs/指示資料/` を確認。README のみ)

## 目的

`updateRecurringRule` が「ルール更新 → 生成済み予定の削除 → 例外の削除」を別々のリクエストで行い、後ろの削除結果を確認せず成功を返している。
削除が失敗すると、ルールは新しい内容なのに古い予定・例外が残る(画面は古い時刻のまま、成功表示)。
3つの操作を1つのDBトランザクションにし、どれかが失敗したら全体を取り消す。

## 現況

- `lib/calendar/recurring.ts` の `updateRecurringRule`(L367〜)が3回の `client.from(...)` を順に呼ぶ。2つ目・3つ目の `error` を見ていない
- 取り消し範囲は「今日以降」(`todayBoundary(timezone)` が返す UTC 閾値と日付)。過去の予定は残す(P5-1)
- 先例: `start_timer` / `stop_timer` は `public` に置いた `security invoker` の関数で、既存RLSを維持している

## 仕様

### DB(マイグレーション `supabase/migrations/<timestamp>_atomic_recurring_rule_update.sql`)

- `public.update_recurring_rule(...)` を追加する。`security invoker`・`set search_path = ''`(RLSをそのまま効かせる。先例と同じ)
  - 引数: ルールid、更新する8列(title / pattern / weekdays / start_time / end_time / timezone / starts_on / ends_on)、
    今日の0時のUTC(`p_threshold timestamptz`)、今日の日付(`p_today date`)
    - 「今日」の境界はタイムゾーン計算を伴うため、これまでどおりアプリ側の `todayBoundary` で求めて渡す(SQLへ移植しない)
  - 処理(1トランザクション): ①ルール更新(`inactivity_since = now()`、`pause_review_after = null`) ②`synced_events` の
    `source = 'app'` かつ `google_event_id` が `rec:<ルールid>:` で始まり `start_at >= p_threshold` の行を削除
    ③`recurring_exceptions` の `rule_id` 一致かつ `occurrence_date >= p_today` の行を削除
  - ①で0行(存在しない・他人のルール)なら、②③を実行せず `false` を返す。それ以外は `true`
  - ②③の失敗は例外のまま伝える(成功へ変換しない)。トランザクションごと取り消される
  - 前方一致は `left(google_event_id, length(prefix)) = prefix` で判定する(`like` のワイルドカードに依存しない)
  - 未認証(`auth.uid()` が null)は例外
- `revoke all ... from public, anon, service_role` のうえ `grant execute ... to authenticated`(P6-5の規約)
- テーブルの追加・列の変更はない

### アプリ

- `updateRecurringRule` は入力検証までは現状どおり。その後の3操作を `client.rpc("update_recurring_rule", ...)` 1回に置き換える
- `error` または戻り値が `true` でない場合は `{ ok: false }`(RPCの例外・0行を区別せず失敗として返す。呼び出し側のUIは既存の失敗表示を使う)
- 戻り値の型・呼び出し側(Server Action・画面)は変更しない

## エラー時の挙動

- DB関数の途中で失敗 → ルール・予定・例外のどれも変わらず、`{ ok: false }` が返る
- 他人のルールid → 何も変更せず `{ ok: false }`(RLSで①が0行)

## スコープ外

- `deleteRecurringRule` の同種の問題(別Issueで扱う。今回は触らない。調査して見つけた場合は記録のみ)
- 再実体化(`materializeRecurringInstances`)の挙動変更

## テストシナリオ

- T1 [結合]: Given 自分のルールと今日以降の生成済み予定・例外 When `updateRecurringRule` で時刻を変更 Then ルールが更新され、
  今日以降の予定・例外が消え、`ok: true`
- T2 [結合]: Given 昨日以前の生成済み予定・例外 When 更新 Then 過去分は残る(既存S21の回帰)
- T3 [結合・境界]: Given `start_at` がちょうど閾値の予定と閾値の1ミリ秒前の予定 When 更新 Then 前者は消え後者は残る。
  例外も `occurrence_date` が今日の行は消え、昨日の行は残る
- T4 [結合・失敗時の取り消し]: Given 例外の削除でエラーを起こす状態(テスト用の `before delete` トリガーで例外を投げる)
  When 更新 Then `ok: false`、ルールは更新前の値のまま、予定も削除されない
- T5 [結合・RLS]: Given 他ユーザーのルールid When 更新 Then `ok: false` で他人のルール・予定・例外は不変(既存S23の回帰)
- T6 [結合]: Given 別ルールの予定(`rec:<別id>:` 始まり)と手動の予定(`source = 'app'` だが `rec:` なし) When 更新
  Then それらは削除されない
- T7 [結合・権限]: Given anon / 未ログインのクライアント When `update_recurring_rule` を呼ぶ Then 権限エラー
  (`table-grants.test.ts` の方式に追加)
- T8 [結合]: 更新後に `inactivity_since` が更新され `pause_review_after` が null になる(既存の仕様の回帰)
- T9 [単体・異常系]: Given RPCが `error` を返す When `updateRecurringRule` Then `ok: false`(例外を握りつぶさない)
- T10 [単体]: Given 不正な入力(空タイトル・不正なid) When 更新 Then RPCを呼ばずに `ok: false`

R-1: 日時を使うテストは `TZ=UTC` と `TZ=Pacific/Kiritimati` でも確認する。
