## 目的

「提案」経由で登録した定期予定について、計測を継続するほど開始時刻・所要時間が実績に自動で
近づいていくことで、ユーザーが手を動かさなくても見積もりの精度が上がっていく体験を提供する。
これにより核心価値「見積もりが当たるようになる」を、提案機能が生む予定についても体現する。

### 決定済みの要件(brainstorming結果)

| 論点 | 決定 |
|---|---|
| 効果 | 提案の開始時刻・所要時間が計測を継続するほど自動で実績に近づく(表示だけでなくロジックが自動調整) |
| 対象範囲 | 「提案」経由で登録した**定期予定のみ**。「この週に追加」の単発予定、Googleカレンダー由来の予定は対象外 |
| スコープ位置づけ | 要件定義書「見積もり係数学習(v2目玉)」の前倒し・具体化。カテゴリ横断の係数学習(「バグ修正は平均2.3倍」等)は引き続きv2本体のスコープ |
| 適用方式 | 自動適用。サイレントにはせず、変更が発生した回だけカレンダー画面にお知らせ帯を表示する |
| 停止トグル | 必要。定期予定ごとに「自動調整を止める」導線を用意し、内部的には対象を`origin='manual'`に戻す |
| 閾値 | 最低3サンプル・7日おきの再学習・15分未満の差は無視 |
| 単発予定への対応 | 「この週に追加」側への provenance 列追加は見送る。単発は毎週`computeSuggestions`が最新28日の実績から再計算するため、既存動作で実質的に最新実績へ寄っており対象外のままでよい |

## 仕様

### 前提として確認した現状の実装

- 単発予定「この週に追加」: `components/plan-suggestions.tsx` → `createAppEventAction`
  (`app/(app)/calendar/event-actions.ts`) → `createAppEvent`(`lib/calendar/app-events.ts`)
  → `synced_events` に `source='app'`, `google_event_id='app:<uuid>'` で1行 INSERT
- 定期予定「毎週にする」: `plan-suggestions.tsx` → `createRecurringRuleAction` →
  `createRecurringRule`(`lib/calendar/recurring.ts`) → `recurring_rules` に定義行を1つ INSERT。
  表示のたびに `materializeRecurringInstances` が `synced_events` へ
  `source='app'`, `google_event_id='rec:<ruleId>:<occurrenceDate>'` として冪等upsert
- `createAppEventAction`/`createRecurringRuleAction` はカレンダー画面・計測画面からの手動予定作成
  とも共用されており、**現状のスキーマには「提案経由かどうか」を示す情報がない**
- `time_entries.google_event_id` は文字列一致でのみ予定と紐づく(外部キーではない)。定期予定の
  1回分なら `rec:<ruleId>:<occurrenceDate>` がそのまま入る

### データモデルの変更

```sql
alter table public.recurring_rules
  add column origin text not null default 'manual'
  constraint recurring_rules_origin_check check (origin in ('manual', 'suggestion'));

alter table public.recurring_rules
  add column last_learned_at timestamptz;
```

- 新テーブルは作らない。カテゴリ横断の係数学習という本来のv2目玉は今回のスコープ外であり、
  既存 `recurring_rules` と `time_entries` の突き合わせだけで完結させる(P5-2の
  「DB変更を最小に保つ」哲学を踏襲)
- 既存テーブルへの列追加のみのため、RLSポリシー変更・新規GRANTは不要(既存ポリシーがそのまま
  `origin`/`last_learned_at` を含む行全体をカバーする)
- `origin`: `'suggestion'` = 提案の「毎週にする」経由で作成。`'manual'`(既定) = それ以外の
  すべての経路(カレンダー画面・計測画面からの手動作成、および学習停止トグルでの明示的な離脱)
- `last_learned_at`: 直近の学習判定日時。`RELEARN_INTERVAL_DAYS` 未満の間隔での再計算を防ぐ
  ゲートとして使う。学習対象になった時点(`origin='suggestion'`でINSERTされた時点)では `null`

### アーキテクチャ概要

```
カレンダーpage (Server Component)
  ├─ fetchSuggestionSourceEntries(既存。P5-2で新設)
  ├─ fetchRecurringRules()                             ← 既存
  ├─ computeRuleAdjustments(rules, entries, now)        ← 新設(lib/calendar/rule-learning.ts、純粋関数)
  ├─ applyRuleAdjustments(client, adjustments, now)     ← 新設。変更ありのルールのみDB更新
  └─ materializeRecurringInstances(既存。更新後の値で実体化)
        └─ props で CalendarView 経由 → お知らせ帯(調整があった回のみ)
```

- 判定(`computeRuleAdjustments`)はカレンダーページのRSCで、既に取得済みの
  `fetchSuggestionSourceEntries` の戻り値と `fetchRecurringRules` の戻り値を渡すだけで完結する
  (追加クエリなし。P6-1「サーバー往復の集約」の方針を踏襲)
- 書き込み(`applyRuleAdjustments`)は変更が実際にある `recurring_rules` 行のみUPDATEし、
  `materializeRecurringInstances` の呼び出し前に反映することで、以降の実体化に新しい値が
  即座に使われるようにする

### 検出・補正ロジック(`lib/calendar/rule-learning.ts` の純粋関数 `computeRuleAdjustments`)

定数:

```ts
const ADJUSTMENT_LOOKBACK_DAYS = 42;   // 直近6週間ぶんの実績を参照
const MIN_SAMPLES_FOR_ADJUSTMENT = 3;  // 中央値の最低信頼性
const ROUND_UNIT_MINUTES = 15;         // suggestions.ts と同じ丸め単位
const RELEARN_INTERVAL_DAYS = 7;       // 再学習の間引き間隔
```

入力: `origin='suggestion'` の `recurring_rules` 一覧、`fetchSuggestionSourceEntries` の
実績配列、現在時刻。出力: `RuleAdjustment[]`(ルールごとの調整結果)。

1. **対象ルールの絞り込み**: `origin === 'suggestion'` かつ、`last_learned_at` が
   `null` または現在時刻から `RELEARN_INTERVAL_DAYS` 日以上前のルールのみ処理する
2. **紐づく実績の抽出**: `time_entries` のうち `google_event_id` が `rec:<ruleId>:` で
   始まり、`startAt` が現在時刻から `ADJUSTMENT_LOOKBACK_DAYS` 日以内のものを対象とする
3. **サンプル数チェック**: 該当実績が `MIN_SAMPLES_FOR_ADJUSTMENT` 件未満なら調整せず
   (`changed: false`)、`last_learned_at` の更新のみ行う
4. **中央値の算出**: ルールのタイムゾーンで、各実績のローカル開始時刻(0:00からの分)と
   所要時間(分)を求め、それぞれの中央値を `ROUND_UNIT_MINUTES` 単位に丸める(最低15分)
5. **変更要否の判定**:
   - 丸め後の終了時刻が日をまたぐ(24:00を超える)場合は調整しない(FR-12の定期予定は
     日またぎ不可のため。P5-2の候補除外条件と同じ制約)
   - 新しい開始時刻・所要時間と現在の登録値との差がいずれも `ROUND_UNIT_MINUTES` 未満なら
     `changed: false`(15分未満の差は無視)
   - それ以外は `changed: true` として新しい `start_time`/`end_time` を返す

### 書き込みロジック(`applyRuleAdjustments`)

- `changed: true` のルールのみ:
  1. `recurring_rules` の `start_time`/`end_time`/`last_learned_at` を更新
  2. 今日以降(`start_at >= 今日のUTC境界`)かつ `source='app'` かつ
     `google_event_id like 'rec:<ruleId>:%'` の `synced_events` 行のみ削除し、
     次回の `materializeRecurringInstances` で新しい値で再実体化されるようにする
- `changed: false` のルールは `last_learned_at` のみ更新
- **既存の `updateRecurringRule`(手動編集用)は使わない**。この関数は編集時に
  今日以降の `recurring_exceptions` も削除する仕様(P5-1)だが、学習による自動調整で
  ユーザーが明示的に「この回のみ削除」した回を勝手に復活させるのは事故のため、
  専用の軽量な更新パスとする。`recurring_exceptions` には一切触れない
- **過去は一切書き換えない**: `synced_events` の削除条件は必ず `start_at >= 今日` を含む。
  過去に計測した実績・過去の予定表示は不変

### `origin` 列のセット方法

- `createRecurringRuleAction`/`createRecurringRule` に `origin` 引数を追加(既定 `'manual'`)
- `plan-suggestions.tsx` の `makeWeekly` のみが `origin: 'suggestion'` を渡す
- `calendar-view.tsx`・`track-view.tsx` からの手動作成呼び出しは無改修(既定値 `'manual'`)

### UI(実装時は ui-quality Skill・375px確認)

- カレンダー画面に、調整が発生した回だけ一時的なお知らせ帯を表示する。
  例:「『朝会』の所要時間を実績にあわせて30分→45分に調整しました」
  (複数件同時に発生した場合は帯を複数行、または件数まとめ表示。詳細はテストシナリオで確定)
- 定期予定の編集パネル(`AppEventPanel` 等の定期予定編集UI)に、`origin='suggestion'` の
  ルールに限り「自動調整を止める」トグルを表示する。ONにすると `origin` を `'manual'` に
  更新し、以降 `computeRuleAdjustments` の対象から外れる(元の値は変更しない。単に以後
  固定化されるだけ)
- `origin='manual'`(元々手動作成)の定期予定にはトグル自体を表示しない
- 文言は `lib/calendar/messages.ts` に集約(日本語)

### エラー時の挙動一覧(すべて日本語。`lib/calendar/messages.ts` に集約)

| 状況 | 挙動 |
|---|---|
| `computeRuleAdjustments` の計算自体は失敗しない(純粋関数・例外を投げない設計) | — |
| `applyRuleAdjustments` のDB更新失敗 | 当該ルールの調整をスキップし、カレンダー本体の描画は妨げない。次回のページロードで再試行される(`last_learned_at` を更新していないため) |
| 学習停止トグルの更新失敗 | パネル内にエラーメッセージを表示し、トグルは元の状態のまま残る |

### セキュリティ

- 新しいデータ取得経路は追加しない。読み取りは既存の `fetchSuggestionSourceEntries`/
  `fetchRecurringRules` の戻り値を再利用し、書き込みは本人の行のみを対象とする既存RLS
  (`recurring_rules`/`synced_events` とも `to authenticated` かつ本人のuser_idのみ)の
  範囲内で行う
- 新規テーブル・ポリシー追加はないため、GRANTの追加も不要

## スコープ外

- カテゴリ横断の見積もり係数学習(「バグ修正は平均2.3倍」等)。引き続き要件定義書のv2本体スコープ
- 単発予定(「この週に追加」)への学習適用
- サマリー画面・計測画面への学習結果の可視化
- 元々手動作成した定期予定を後から学習対象(`origin='suggestion'`)に切り替える導線
  (将来ニーズが出た場合に別タスクで検討)
- 学習によって行われた調整の履歴(いつ・どう変わったか)の永続化・一覧表示
