# 仕様書: サマリー長期間集計の行数上限バグ修正(P6-0)

- ステータス: 承認済み(2026-08-06)
- 関連: docs/要件定義書.md FR-09(ギャップサマリー) / docs/specs/P5-9_サマリーの任意期間表示.md
- 指示資料: なし(`docs/指示資料/` を確認。関連資料なし)

## 目的

サマリーの任意期間表示(P5-9)で、**集計値が黙って誤る**可能性を解消する。

`app/(app)/summary/page.tsx` は最大 366 日ぶん(`lib/summary/range.ts` の `MAX_RANGE_DAYS = 366`)の
`synced_events` / `time_entries` を `.limit()` なしで取得している。
PostgREST には `max_rows` の上限があり(`supabase/config.toml` のローカル設定では `1000`)、
これに達すると **エラーを返さずに黙って打ち切られる**。
打ち切られた行は `computeGapSummary` に渡らないため、予定時間・実績時間・ズレがすべて過小に出る。
ユーザーには正常な集計に見えるため、誤りに気づけない。

1 日 3 件の予定 × 1 年 = 1095 行で上限を超えるため、
「カスタムで 1 年」を選ぶ実運用ユーザーは現実的に踏みうる。

これは性能ではなく**正しさ**の問題であり、パフォーマンス改善(P6-1〜P6-4)より先に修正する。

## 現状の実装

| ファイル | 該当 | 問題 |
|---|---|---|
| `lib/calendar/events.ts` `fetchSyncedEventsInRange` | `.lt/.gt/.order` のみ | `.limit()` / `.range()` なし。1 回のクエリで全件取れる前提 |
| `lib/timer/entries.ts` `fetchTimeEntriesInRange` | 同上 | 同上 |
| `app/(app)/summary/page.tsx` | `Promise.all` で両者を呼ぶ | 取得件数の検証なし |

`fetchSyncedEvents` / `fetchTimeEntries`(カレンダー・計測画面用)は上記のラッパで、
期間が「週 ± 1 週間 = 21 日」に固定されているため現実的に上限へ届かない。ただし同じ経路を通る。

## 仕様

### 1. ページング取得にする

`fetchSyncedEventsInRange` / `fetchTimeEntriesInRange` を、
`.range(offset, offset + PAGE_SIZE - 1)` を使ったループ取得に変える。

- `PAGE_SIZE = 1000`(PostgREST の既定 `max_rows` と一致させる)
- 返却行数が `PAGE_SIZE` 未満になったら終了
- 返却する型(`SyncedEvent[]` / `TimeEntryItem[]`)・カラム集合・フィルタ条件は**変更しない**

**ソートキーの一意化(実装中に判明した必須事項)**:
既存の `.order("start_at", { ascending: true })` だけでは不十分。
`start_at` が同値の行(同時刻に始まる予定・実績は普通に存在する)があると、
LIMIT/OFFSET のページ間で Postgres の返す順序が不定になり、**行の重複・欠落が起きる**。
第 2 ソートキーとして一意な `id` を追加し、`.order("start_at").order("id")` とする。
同一 `start_at` 内の並びが id 順に確定するだけで、既存の表示順(start_at 昇順)は変わらない。

### 2. 総行数の安全弁

無制限にページを取り続けてメモリと時間を消費しないよう、上限を設ける。

- `MAX_FETCH_ROWS = 20000`(1 日 50 件 × 366 日を上回る値。実運用では到達しない想定)
- 超過した時点で取得を中断し、`RowLimitExceededError` を投げる
- **黙って打ち切ることはしない**。これが本バグの再発防止そのものであるため、必ず失敗させる

`RowLimitExceededError` は `lib/errors/row-limit.ts` に新設し、
`fetchSyncedEventsInRange` / `fetchTimeEntriesInRange` の両方から投げる。

### 3. サマリー画面のエラー表示

`app/(app)/summary/page.tsx` のデータ取得を `try` / `catch` で囲み、
`RowLimitExceededError` を捕捉したら集計せず、既存の `rangeTooLong` と同じ体裁で日本語メッセージを出す。

- 新規メッセージ: `SUMMARY_MESSAGES.rangeTooManyRows`
  = `"この期間はデータが多すぎて集計できません。期間を短くして表示し直してください"`
- 表示は既存の `data-testid="summary-range-error"` のブロックを再利用する
  (期間タブ・前後移動は従来どおり操作できる状態を保つ)
- `RowLimitExceededError` 以外のエラーは従来どおり再送出し、エラー境界(`app/error.tsx`)に任せる

### 4. ホスト環境の `max_rows` 確認

`supabase/config.toml` はローカル用の値。本番 Supabase の API 設定にある `Max rows` の実値を確認し、
`PAGE_SIZE` が実値以下であることを仕様書とログに記録する
(`PAGE_SIZE` が実値を上回ると「PAGE_SIZE 未満だから最終ページ」の判定が誤り、取りこぼす)。
**確認はユーザー作業**とし、確認できるまで `PAGE_SIZE = 1000` を採用する
(Supabase の既定値であり、これを下回る設定にしている環境は通常ない)。

## スコープ外

- **サマリー集計の DB 側 RPC 化**(行転送量そのものの削減)。本バグは正しさの問題であり、
  ページングで解決する。転送量の最適化は効果を実測してから別途判断する(P6-2 以降で再評価)
- **`MAX_RANGE_DAYS` の変更**。366 日という上限は P5-9 でユーザー承認済みの仕様であり、変えない
- **重なり判定クエリへの下限追加**(全履歴スキャンの解消)。P6-2 で扱う
- **`/calendar` `/track` のページング挙動の変更**。ラッパ経由で同じ実装を通るため自動的に恩恵を受けるが、
  期間が 21 日固定のため実質的な変化はない

## テストシナリオ

### 単体(`tests/lib/calendar/events.test.ts` / `tests/lib/timer/entries.test.ts`)

Supabase クライアントをモックし、ページングループの制御を検証する。

- **S1 [単体]**: Given 該当行が 0 件 When `fetchSyncedEventsInRange` を呼ぶ
  Then 空配列を返し、クエリは 1 回だけ発行される
- **S2 [単体]**: Given 該当行が 999 件(PAGE_SIZE 未満) When 呼ぶ
  Then 999 件を返し、クエリは 1 回だけ発行される
- **S3 [単体] 境界値**: Given 該当行がちょうど 1000 件 When 呼ぶ
  Then 1000 件を返す。2 ページ目(0 件)まで取得するためクエリは 2 回発行される
- **S4 [単体] 境界値**: Given 該当行が 1001 件 When 呼ぶ
  Then 1001 件すべてを `start_at` 昇順で返し、クエリは 2 回発行される
- **S5 [単体]**: Given 該当行が 2500 件 When 呼ぶ Then 2500 件すべてを返す(3 ページ)
- **S6 [単体] 異常系**: Given 該当行が `MAX_FETCH_ROWS` を超える When 呼ぶ
  Then `RowLimitExceededError` を投げる(部分的な結果を返さない)
- **S7 [単体] 異常系**: Given 2 ページ目のクエリが DB エラーを返す When 呼ぶ
  Then 既存と同じ日本語メッセージ(`"予定の読み込みに失敗しました"`)で例外になる
- **S8〜S14 [単体]**: S1〜S7 と同じ内容を `fetchTimeEntriesInRange` について検証する
  (`"実績の読み込みに失敗しました"`、`.not("end_at", "is", null)` 条件が維持されること)

### 結合(`tests/integration/summary-row-limit.test.ts` 新規)

ローカル Supabase + RLS 経由で、実際に打ち切りが起きること・修正後に起きないことを検証する。

- **S15 [結合] 再現(修正前は失敗する)**: Given 同一ユーザーの `synced_events` に
  期間内の予定を 1200 件投入する When `fetchSyncedEventsInRange` を期間全体で呼ぶ
  Then 1200 件すべてが返る
- **S16 [結合] 再現(修正前は失敗する)**: Given 同一ユーザーの `time_entries` に
  期間内の確定済み実績を 1200 件投入する When `fetchTimeEntriesInRange` を呼ぶ
  Then 1200 件すべてが返る
- **S17 [結合] 集計の正しさ**: Given S15 と同じ 1200 件(1 件 60 分の予定)
  When `computeGapSummary` に渡す Then 合計予定時間が 1200 × 60 分になる
  (打ち切られていれば 1000 × 60 分になり失敗する)
- **S18 [結合] RLS**: Given ユーザー A に 1200 件、ユーザー B に 10 件を投入する
  When ユーザー B の文脈で呼ぶ Then B の 10 件のみが返る(ページングが RLS を迂回しないこと)
- **S19 [結合] 順序**: Given 1200 件を `start_at` がばらけるように投入する
  When 呼ぶ Then 返却順が `start_at` 昇順で、ページ境界(1000 件目と 1001 件目)でも順序が保たれる
- **S19 [結合] 順序の一意性**: Given 1200 件すべてを**同一の `start_at`** で投入する
  When 呼ぶ Then 1200 件が重複・欠落なく返る(第 2 ソートキーがなければ失敗する)
