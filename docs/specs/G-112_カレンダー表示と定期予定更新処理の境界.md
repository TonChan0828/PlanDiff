# 仕様書: G-112 カレンダー表示と定期予定の更新処理の境界を明確にする

- ステータス: 承認済み(2026-11-25)

- 指示資料: なし(2026-11-25 に `docs/指示資料/` を確認。README のみ)

## 目的

`/calendar` のページが、定期予定の生成・自動調整・再生成・画面用データの読み取りを順に実行しており、書き込みの順序と失敗時の扱いが表示処理に埋もれている。
書き込みの手順をサーバー側のサービスにまとめ、順序と失敗時の扱いを明示する。同時表示・再試行での整合を、結合テストで確かめる。

## 現況(2026-11-25 実測)

`app/(app)/calendar/page.tsx` が次を順に行う:

1. `materializeRecurringInstances`(定期予定の実体化。`synced_events` へ upsert)を、`profiles` の取得と並列で実行
2. 自動調整が有効なルールがあれば `computeRuleAdjustments` → `applyRuleAdjustments`(RPC `apply_recurring_rule_learning`)
3. 調整が1件でもあれば、結果をマージしたルールで `materializeRecurringInstances` を再実行(読み直さない。Next.js の fetch メモ化で更新前を返すため)
4. `fetchSyncedEvents` ほか画面用データを読み取り、`CalendarView` へ渡す

### 調査で分かったこと

- **`apply_recurring_rule_learning` は原子的で、再実行しても安全**。`recurring_rules` 行を `for update` で確定し、「前回の時刻と一致」「最後の学習から7日以上」「休止中でない」を満たすときだけ更新する。
  同じ調整が2リクエストから来ても、後から来た側は前回の時刻が一致せず `false` になる
- **実体化の upsert は `ignoreDuplicates: true`**(キー `user_id, google_event_id`)。同じ日付の行が既にあれば、時刻が古くても上書きしない
- **競合の可能性(要・結合テストでの再現)**: リクエストAが調整して、今日以降の `synced_events` を削除する間に、リクエストBが「調整前のルール」で実体化すると、
  古い時刻の行が再挿入される。A の再実体化は `ignoreDuplicates` のため、その古い行を上書きできず、新しい時刻のルールに古い時刻の予定が残りうる

## 仕様

### サービス化

- `lib/calendar/recurring-sync.ts` を新設し、`prepareRecurringEvents(client, { baseDate, now })` を置く。ページの手順 1〜3 をそのまま移し、
  `{ recurringRules, ruleAdjustments }` を返す。ページはこれを呼び、手順 4(画面用データの読み取り)と表示だけを持つ
- 書き込みの順序を、サービスの冒頭コメントと本仕様に明示する:
  1. 実体化(冪等。失敗しても既存の表示は続ける)
  2. 自動調整(ルールごとに独立。1件の失敗・不一致は他のルールへ波及させない)
  3. 調整があったルールだけを対象に再実体化(失敗しても調整済みのルールと通知は維持し、予定の再生成は次回表示で補う)
- 失敗時の扱い: 例外でページ全体を落とさない現行の方針を維持する。失敗は呼び出し側へ値で返すのではなく、既存どおり `console.error` に記録する
  (観測性の変更は本仕様のスコープ外)
- `page.tsx` のオンボーディング判定(`profiles` の並列取得)と `redirect` の位置は変えない(P6-1 の往復数のテスト `page-waterfall.test.tsx` を維持する)

### 実装で確定した事項(2026-11-26)

- **【訂正】** 初版の仕様は「`rec:` の行は手編集の経路がないため上書きしてよい」としていたが、誤りだった。`updateAppEvent`(「この予定のみ」の編集)は `rec:` の行のタイトル・時刻を個別に変えられる。
  独立レビューで、新しく計算した行の時刻(`>= now`)で上書き可否を決めると、始まった回や過去に移した個別編集を消すことが分かった(結合テスト B13 で再現)。
  そのため、上書きの可否は**既存行の開始**で判定する(調整の RPC が削除する範囲と同じ)。調整後の開始が `now` より前に早まる場合も、調整前の時刻で入り直した行を整えられる(B14)

- **競合は結合テスト B10 で再現した**(調整の削除のあと、調整前ルールで実体化すると、今日以降の行に古い時刻 09:00 が残り、再実体化後も `ignoreDuplicates` のため上書きされなかった)。
  承認済みの方針に従い、`materializeRecurringInstances` に省略可能な第5引数 `{ overwriteRuleIds, overwriteFrom }` を追加し、調整したルールの今日以降の行だけを上書きする(既定は従来どおり上書きしない)
- 自動調整(書き込み)は、オンボーディング済みと分かってから行う。ページは実体化と `profiles` 取得を並列に走らせるため、サービスは `canAdjust: Promise<boolean>` を受け取り、
  実体化の後で待つ。これにより、オンボーディング前のユーザーには従来どおり調整の書き込みが走らない
- 再実体化(`rematerializeAdjustedRules`)の失敗は例外にせず、`console.error` に記録して調整済みのルールと通知を返す(B5)

### 整合性の確保(調査結果に応じて)

- 結合テストで、上の競合(調整の削除と、調整前ルールでの実体化の交錯)を**まず再現する**(Red)
- 再現できた場合の修正方針(承認を求める): 調整直後の再実体化で、調整したルールの行を**上書き**する(`ignoreDuplicates: false`)。
  **上書きの対象は、DB にある既存行の開始が `now` 以降のものだけ**(調整の RPC が削除する範囲と同じ)。始まった回・過去の回は触らない
- 再現できなかった場合は、挙動を変えず、テストを回帰として残す(仕様書に結果を記録する)

## エラー時の挙動

- 現行と同じ。実体化・調整の失敗でカレンダーを落とさず、取得できる範囲で表示する

- **【追補・不具合修正】** 初回の実装は「上書き対象を確認 → 挿入のみ → 上書き」の順で、確認と挿入の間に別リクエストが調整前の行を入れると、その行が残った(CI の B8 が失敗して発覚)。
  順序を「**全行を挿入のみで書く → 上書き対象を確認 → 上書き**」にした。挿入後は全ての回に行があり、あとから届く古い挿入は無視されるため、確認の漏れがない。
  テストシナリオ B17 [単体]: 再実体化の `synced_events` への各操作の直前に古い挿入が割り込んでも、最終的に新しい時刻にそろう

## 残る限界(スコープ外として承知しているもの)

- 再実体化が上書きするのは、このリクエストが実体化する範囲(基準日の週 ±1週間)だけ。調整の RPC は今日以降の行を全期間で削除するため、
  別の範囲を表示している別リクエストが調整前のルールで古い時刻の行を入れ直した場合、その範囲の行は以後も上書きされずに残る。
  窓は調整の削除から再実体化までの短い間で、同じ範囲(通常の同時表示)は B10 で整合することを確認している。範囲外の完全な整合には、調整の RPC 側で全期間を再生成するなど、DB の変更が要る(別途判断)
- 調整の RPC が個別編集済みの「今日以降の回」を削除する(既存の仕様)ことは変えない

## スコープ外

- `applyRuleAdjustments` の内部・RPC・DB の変更(原子的で、調査の結果、変更の必要はない)
- ルール調整の通知(お知らせ帯)の文言・表示の変更
- 休止提案(`fetchRulePauseSuggestions`)の取得位置の変更(表示用データの読み取りに含める)

## 確認事項(承認時に判断してください)

1. 競合が再現できた場合に、調整直後の再実体化を「今日以降の行の上書き」にする方針でよいか(DB変更なし。`ignoreDuplicates` の引数変更のみ)

## テストシナリオ

時刻は固定し、日時はローカルTZで組み立てる(R-1)。

- B1 [単体]: Given 自動調整が有効なルールがない When `prepareRecurringEvents` Then 実績の取得も調整もせず、実体化の結果のルールを返す
- B2 [単体]: Given 調整が0件 When 実行 Then 再実体化しない(実体化は1回)
- B3 [単体]: Given 調整が1件 When 実行 Then 調整後に、調整結果をマージしたルールで再実体化し、ルールを読み直さない(P6-1 のメモ化対策)
- B4 [単体・異常系]: Given `applyRuleAdjustments` が一部のルールで `false` を返す When 実行 Then 成功したルールだけが `ruleAdjustments` に入り、他は影響を受けない
- B5 [単体・異常系]: Given 再実体化が失敗(upsert エラー) When 実行 Then 例外にせず、調整済みのルールと通知を返す
- B6 [単体]: 呼び出しの順序が「実体化 → 調整 → 再実体化」である(モックの呼び出し順で固定)
- B7 [画面]: 既存の `page.test.tsx`・`page-waterfall.test.tsx` が、サービス化後も全件合格する(表示結果・調整通知・往復数が現行どおり)
- B8 [結合]: Given 同じ期間を同時に2リクエストで表示(`Promise.all`)When 実体化・調整が走る Then `synced_events` に同じ `google_event_id` の重複がなく、ルールの時刻は1回だけ更新される
- B9 [結合・再試行]: Given 調整が完了した後に、もう一度同じ表示 When 実行 Then 追加の変更が起きない(冪等)
- B10 [結合・競合の再現]: Given リクエストAの調整(今日以降の削除)と、リクエストBの「調整前ルールでの実体化」が交錯 When A の再実体化まで完了 Then 今日以降の `synced_events` がすべて新しい時刻になっている
  (現行コードでは古い時刻の行が残る可能性がある。Red で確認し、整合方針に従って直す)
- B11 [結合]: 過去の行(今日より前)は、調整・再実体化のどちらでも変わらない
- B12 [結合・RLS]: 他ユーザーのルール・予定は読み書きされない(既存の方式で回帰)
- B13 [結合・レビュー指摘]: Given 開始済みの回を「この予定のみ」で個別編集済み When 調整後に再実体化 Then その回のタイトル・時刻は上書きされない
- B14 [結合・レビュー指摘]: Given 調整で開始が現在より前に早まる(09:15 → 09:00、現在 09:10)When 調整の削除のあとに調整前のルールで入り直す Then 再実体化で今日の行が新しい時刻(09:00)にそろう
- B16 [単体・上書きオプション]: オプション省略時は既存行を確認せず従来どおり / 対象ルールの行がなければ確認しない / 既存行として返った id だけを上書き / 既存行の確認に失敗したら上書きせず挿入のみ(安全側) / 上書き側の upsert が失敗しても挿入側は保たれ例外にしない
- B15 [画面]: オンボーディング前のユーザーには調整の書き込み(rpc)を行わず、オンボーディング済みなら学習判定の rpc を行う。プロフィールの取得は1回だけ送る(クエリの `then` を1回しか呼ばない)

R-1: 日時が絡むテストは `TZ=UTC` と `TZ=Pacific/Kiritimati` でも実行する。
