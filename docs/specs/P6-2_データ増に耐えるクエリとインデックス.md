- 関連: docs/開発計画.md Phase 6 / docs/specs/P6-0_サマリー集計の行数上限.md

## 目的

**使うほど確実に遅くなる構造**を解消する。今は速いが、データが増えると必ず劣化する。

`fetchSyncedEventsInRange` / `fetchTimeEntriesInRange` の重なり判定は次の形をしている。

```ts
.lt("start_at", range.timeMax)
.gt("end_at", range.timeMin)
```

RLS と合わせた実効述語は `user_id = $1 AND start_at < timeMax AND end_at > timeMin`。
`synced_events_user_start_idx (user_id, start_at)` は **`start_at < timeMax` の片側境界しか使えず**、
`end_at > timeMin` はヒープ取得後のフィルタになる。
つまり**1 週間ぶんの表示のために、そのユーザーの timeMax 以前の全履歴を読む**。

### 実測(ローカル Postgres、3 年ぶん約 11,000 行)

```
=== 現状のクエリ ===
Seq Scan on ev (rows=210)
  Filter: (user_id = ... AND start_at < now() AND end_at > now() - '21 days')
  Rows Removed by Filter: 10751          ← 210件を返すために全行を読んでいる
Execution Time: 0.843 ms

=== tstzrange 生成列 + GiST インデックス ===
Bitmap Index Scan on ev_user_span (rows=210)
  Index Cond: (user_id = ... AND span && tstzrange(...))
Execution Time: 0.060 ms                 ← 約14倍。全件走査が消える
```

3 年使ったユーザーは毎回 1,000 日ぶんをスキャンして 21 日ぶんだけ返している。

## 承認済みプランからの変更(重要)

`docs/開発計画.md` 登録時のプランでは、2-A を
**「予定の最大継続時間を 7 日と仮定し、`start_at` に下限を足す」** としていた。
**これを取り下げ、範囲型 + GiST インデックスに変更する。**

| | 下限を足す案(当初) | 範囲型 + GiST(本仕様) |
|---|---|---|
| 効果 | O(履歴) → O(期間) | 同じ(実測で確認済み) |
| 正しさ | **7 日を超える予定を取りこぼす** | 取りこぼしなし。重なり判定の意味を厳密に保つ |
| DB 変更 | 不要 | 生成列 + `btree_gist` 拡張 + GiST インデックス |
| アプリ変更 | フィルタ 1 行追加 | `.overlaps()` への置換 |

**取り下げる理由**: 7 日仮定は「条件に合う行が黙って結果から消える」という、
P6-0 で修正したばかりのバグとまったく同じ種類の欠陥を持ち込む。
長い予定(合宿・出張・終日連続イベント)は現実に存在し、消えても誰も気づけない。
DB 変更のコストを払ってでも、仮定を置かない方式を採る。

`btree_gist` 拡張の利用可否・生成列・GiST インデックスの作成は、ローカル Supabase で動作確認済み。
`supabase-js` の `.overlaps(column, '[a,b)')` が範囲型に対応していることも確認済み。

## 仕様

### 2-A: 範囲型の生成列と GiST インデックス(マイグレーション)

```sql
create extension if not exists btree_gist;

alter table public.synced_events
  add column span tstzrange
  generated always as (
    case
      when start_at = end_at then tstzrange(start_at, end_at, '[]')
      else tstzrange(start_at, end_at, '[)')
    end
  ) stored;

create index synced_events_user_span_idx
  on public.synced_events using gist (user_id, span);
```

`time_entries` にも同じ列とインデックスを作る。
`end_at` が NULL(実行中タイマー)のとき `tstzrange(start_at, null)` は上端非有界 `[start,)` になり、
「まだ終わっていない」という意味と一致する。

**`case` を入れている理由**: `[x,x)` は**空範囲**で、空範囲は何とも重ならない。
DB の CHECK は `end_at >= start_at` なのでゼロ長の行は作りうる
(`app-events.ts` は開始 < 終了を強制するが、タイマーの即時停止や Google 側の予定は該当しうる)。
`case` がないとゼロ長の予定・実績が**一覧から黙って消える**。

**テーブル書き換えについて**: `ADD COLUMN ... GENERATED ALWAYS ... STORED` はテーブルを書き換える。
現時点のデータ量では問題にならないが、マイグレーション適用時に一時的なロックが発生することを記録しておく。

### 2-B: クエリの置換

`lib/calendar/events.ts` / `lib/timer/entries.ts` の重なり判定を差し替える。

```ts
.overlaps("span", `[${range.timeMin},${range.timeMax})`)
```

- `fetchSuggestionSourceEntries`(`.gte("start_at").lt("start_at")`)は**変更しない**。
  両側境界がすでにあり `(user_id, start_at)` が効いている
- `app/api/calendar/sync/route.ts` の 2 箇所も同じ置換を行う
- **既存の `(user_id, start_at)` インデックスは残す**。`fetchSuggestionSourceEntries` と
  `recurring.ts` の `.gte("start_at", ...)` が使う

#### 境界セマンティクスの差分

| ケース | 現状 `start_at < max AND end_at > min` | `span && [min,max)` |
|---|---|---|
| 通常の重なり | 一致 | 一致 |
| 期間の直前に終わる予定(`end_at == min`) | 除外 | 除外 |
| 期間の直後に始まる予定(`start_at == max`) | 除外 | 除外 |
| ゼロ長で `start_at == min` | 除外 | **含む** |
| ゼロ長で期間内 | 含む | 含む |

差が出るのは「ゼロ長かつ開始が期間の下端ちょうど」の 1 ケースのみ。
包含する側が自然なので受け入れ、テストで固定する。

### 2-C: 補助インデックス(マイグレーション)

```sql
-- .eq("source", ...) を使う sync route / recurring.ts 用
create index synced_events_user_source_start_idx
  on public.synced_events (user_id, source, start_at);

-- rec:<ruleId>:% の前方一致 LIKE(recurring.ts)。既定コレーションのUNIQUEでは使えない
create index synced_events_gei_pattern_idx
  on public.synced_events (user_id, google_event_id text_pattern_ops);

-- 書き込み専用で無制限に増え、集計は必ず seq scan
create index pro_interest_events_type_created_idx
  on public.pro_interest_events (event_type, created_at desc);
```

### 2-D: RLS ポリシーへの `TO authenticated` 付与(マイグレーション)

全 18 ポリシー(`synced_events` / `time_entries` / `profiles` / `recurring_rules` /
`recurring_exceptions`)が `to` 句を省略しており、暗黙で `PUBLIC`(`anon` 含む)に適用される。
`to authenticated` を明示すると未認証リクエストでポリシー評価自体がスキップされる。
`anon` に GRANT していないため**挙動は変わらない**。

## スコープ外

- **`synced_events.recurring_rule_id` 列の正規化**。`rec:<ruleId>:<date>` の文字列パースをやめる
  本命の設計だが、既存データの移行を伴うため別途
- **`(user_id, start_at)` インデックスの削除**。2-A 後も他のクエリが使うため残す
- **サマリー集計の DB 側 RPC 化**。正しさは P6-0 のページングで担保済み

## テストシナリオ

### 単体(`tests/lib/calendar/events.test.ts` / `tests/lib/timer/entries.test.ts` に追加)

- **S1 [単体]**: Given 期間 When `fetchSyncedEventsInRange` を呼ぶ
  Then `.overlaps("span", "[timeMin,timeMax)")` が適用され、`.lt("start_at")` / `.gt("end_at")` は使われない
- **S2 [単体]**: 同上を `fetchTimeEntriesInRange` について。`.not("end_at","is",null)` は維持される
- **S3 [単体]**: Given ページング(P6-0)と併用 When 1001 件返る Then 2 ページ取得され全件返る
  (`.overlaps()` 置換でページングが壊れないこと)

### 結合(`tests/integration/range-overlap.test.ts` 新規)

- **S4 [結合] 通常**: Given 期間と重なる予定・期間外の予定 When 取得する Then 重なるものだけが返る
- **S5 [結合] 境界**: Given `end_at` が期間開始ちょうどの予定 When 取得する Then 返らない(現状と同じ)
- **S6 [結合] 境界**: Given `start_at` が期間終了ちょうどの予定 When 取得する Then 返らない(現状と同じ)
- **S7 [結合] 長い予定**: Given 期間全体をまたぐ 30 日間の予定 When 7 日間の期間で取得する
  Then **返る**(当初案の 7 日仮定では取りこぼしていたケース)
- **S8 [結合] ゼロ長**: Given `start_at == end_at` の予定が期間内にある When 取得する Then 返る
  (生成列の `case` がないと消える)
- **S9 [結合] 実行中タイマー**: Given `end_at` が NULL の実績 When `fetchTimeEntriesInRange` で取得する
  Then 返らない(実行中は確定済み実績に含めない既存仕様)
- **S10 [結合] RLS**: Given ユーザー A / B のデータ When B の文脈で取得する Then B のぶんだけ返る
- **S11 [結合] 実行計画**: Given 期間クエリ When `EXPLAIN` を取得する
  Then `synced_events_user_span_idx` が使われ、`Seq Scan` にならない

### マイグレーション(`tests/integration/core-schema.test.ts` に追加)
