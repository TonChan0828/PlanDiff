# 仕様書: P16 通知と認証の信頼性

- ステータス: 承認済み(2026-09-30。改善一覧の実装指示)
- 関連: P13-1 計測しっぱなしの検知とPush通知 / P1-3 メール認証 / P4-2 設定画面
- 指示資料: docs/指示資料/README.md のみ。追加資料なし

## 目的

Pushへの任意URL登録、アカウント切替後の購読不整合、通知保存失敗の成功扱い、1,000件超の取得漏れ、メール再送のコールバック欠落を解消する。

## 仕様

- 登録先は HTTPS の正規Pushサービス(FCM、Mozilla Autopush、Apple Web Push、Windows Push)に限定する。任意ポート・userinfo・フラグメント・IP・紛らわしいホストを拒否する。URLは2,048文字まで。
- p256dhは65byteの有効な非圧縮P-256公開鍵、authは16byteのbase64url。timezoneは有効なIANA名、リクエストは8KBまで。
- 新しいendpointは1アカウント最大10件。DBトリガーが受取ユーザー単位でロックし並列リクエストにも適用する。同じendpointの更新は上限時も可能。移行時に既存endpointは削除しないため、既に10件を超えるアカウントは10件以下になるまで新規登録できない。既存RLS/GRANTを維持しクライアントにはDBを公開しない。
- 購読確認は認証必須POSTのmode=checkで行い、endpointをURL/ログへ含めない。レスポンスは本人の購読が存在するかのbooleanだけ。他人の識別子や鍵は返さない。すべてno-store。
- 登録・確認成功でこの端末の購読IDをHttpOnly/SameSite=Lax cookieに保持する。ログアウトはuser_idとcookie IDの両方でその端末の行だけを削除し、cookieを破棄する。DB削除失敗時はログアウトを完了扱いせず再試行を案内する。他端末の購読を削除せず、Service Workerは残す。
- UIはブラウザ購読とサーバーの本人購読の両方が存在するときのみ有効と表示する。不一致のブラウザ購読は解除し、再登録導線を表示する。確認失敗を「無効」と断定せず、再確認を案内する。
- POST保存失敗時はブラウザ購読をロールバックし再試行を可能にする。subscribeやネットワーク失敗をブラウザ権限の拒否と混同しない。
- cronはid順のkeyset pagingで全対象を取得する。DB失敗は空配列に変換しない。取得失敗・通知済みマーカー保存失敗・削除失敗をエラーとして伝播し、失敗を含むcronは503を返す。送信成功かつマーカー更新成功の場合のみnotifiedを加算する。
- Push送信には5秒のsocket timeoutを設定し、保存済みの不正なendpoint/鍵にも送信しない。
- 確認メール再送にも新規登録と同じ `${origin}/auth/confirm` を指定する。
- DB/cronのログはイベント名・安全なエラーコードのみ。endpoint・鍵・作業タイトル・メール等はログへ出さない。

## スコープ外

Google連携凍結解除、メール通知追加、cron頻度変更、プロバイダからのPush実到達保証、本番DBへの適用。

## テストシナリオ

- N1 [単体]: 正規サービスURLと有効鍵は受理し、IP/偽装ホスト/http/不正な鍵/過大入力を拒否する。
- N2 [結合]: 不正登録は400、本人の正常登録は204で、同一endpoint更新は重複しない。
- N3 [結合]: 10購読時に新しいendpointは429、既存endpoint更新は204。9購読から並列登録しても10を超えない。
- N4 [結合]: mode=checkは本人の存在booleanのみを返す。他ユーザー/未登録はfalse、未認証は401。成功時だけ購読cookieが設定される。
- N5 [単体]: ブラウザ購読があるがサーバーに本人購読がなければ有効と表示せず、古いブラウザ購読を解除する。
- N6 [単体]: 登録保存失敗時はunsubscribeされ、日本語エラーと再登録導線を表示する。確認API失敗時は再確認可能。
- N7 [単体]: subscribe失敗は権限ブロックと区別され、再試行できる。
- N8 [結合]: ログアウトは本人のcookieに対応する購読のみ削除し、別端末・他ユーザーの購読を残す。cookieなしもログアウト可能。
- N9 [単体]: ログアウト購読削除失敗ならセッションを維持してエラーへ戻る。
- N10 [単体]: 1,001件の候補をページングで全取得し、同じ行を重複取得しない。
- N11 [単体]: 候補取得失敗は503。購読取得/マーカー保存/失効購読削除失敗を成功件数に入れない。
- N12 [単体]: 正常Push送信にtimeoutを設定し、タイムアウトは失敗を返す。保存済みの不正な送信先には送信しない。
- N13 [単体]: 確認メール再送に /auth/confirm が指定される。
- N14 [結合]: cron→DBで検知・送信・マーカー更新、権限不足/対象なし/失効購読削除の既存シナリオを維持する。

## 検証記録

- 通知・認証のfocused tests 50件と全体`npm run check`(unit 901件、本番build含む)が合格。
- migrationの静的レビューは合格。Docker daemonが利用できず、N2〜N4/N8/N14等のローカルDB結合テストとmigration reset/diffは未実施。Production DBへ適用していない。
- Production環境変数名だけを読み取り確認。Supabase接続用3変数とVercel Cron設定は存在し、`NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `CRON_SECRET` は未登録。値は取得・記録していない。
- 既存の購読行は移行で削除しない。移行前から10件を超える利用者は、10件以下になるまで新規endpointを追加できない。
