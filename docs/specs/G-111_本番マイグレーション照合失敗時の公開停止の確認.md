# 仕様書: G-111 本番マイグレーションの照合失敗時に Vercel の公開を止める(確認と運用記録)

- ステータス: 承認済み(2026-11-24)
- 関連: GitHub Issue #111(優先度P1・運用) / [運用手順 P17-2](../運用/P17-2_本番migration適用前デプロイゲート.md) / `.github/workflows/production-migration-gate.yml`
- 指示資料: なし(2026-11-24 に `docs/指示資料/` を確認。README のみ)

## 目的

「照合が失敗または未完了なら Vercel の本番公開が保留される」ことを確認し、設定されていなければ設定する。
照合の範囲(履歴のみ)と、範囲外(テーブル定義・権限のずれ)を確認する運用を記録する。

## 現況

- 設定(Vercel の Project Settings → Deployment Checks)は Dashboard のみで、リポジトリからは読めない。Vercel CLI/API で確認できる範囲を実測する
- 過去の実績: 2026-10-25(S-5)にマイグレーション未適用のままマージし、Vercel 側で Production deployment の check が失敗扱いになった(`docs/logs/2026-10-25.md`)。
  → ゲート自体は機能していた可能性が高いが、設定の画面確認と成功側(公開される)の記録が残っていない
- 運用手順に「Re-run で自動昇格する」とあるが、実際は `vercel promote` が必要だったことがある(S-5)。P10-3 では 409(昇格済み)で、挙動が一定でない

## 仕様

1. **設定の確認**: Vercel の Deployment Checks に `Production migration history`(workflow `Production migration readiness`)が登録されているかを、
   Vercel MCP/CLI の読み取りと、過去 deployment の check 状態で確認する。Dashboard でしか見えない場合は**ユーザーに画面の確認を依頼**する
   (Dashboard の設定変更は私からは行わない)
2. **成功・失敗の実証**: 新しい本番影響のある実験は行わない。次の実績をログから集めて根拠にする
   - 失敗側: 2026-10-25 の保留(S-5)
   - 成功側: P10-3(2026-11-21)など、照合成功後に公開された deployment
   これで足りない場合に限り、プレビュー環境での検証をユーザーに相談する(本番の保護設定を一時的に変えることはしない)
3. **運用手順の更新**(`docs/運用/P17-2_...md`):
   - 照合の範囲は「`supabase/migrations/` のファイル名タイムスタンプと本番履歴の一致」のみ。テーブル定義・権限・RLS のずれは検出しないことを明記
   - 範囲外を確認する運用: マイグレーションを含むリリースの前後に `npx supabase db diff --linked`(読み取りのみ)でずれを確認する手順を追加する
   - 「Re-run で自動昇格」の記述を実績に合わせて修正する(昇格しない場合は `vercel promote`、409 は昇格済み。確認手順つき)
   - 設定の確認方法(どの画面で何が登録されていれば正しいか)を追加する

## エラー時の挙動

- 設定が未登録と判明した場合は、設定手順(既存の運用手順 §Vercel Deployment Checks)をユーザーへ案内し、設定後に再確認する

## スコープ外

- Vercel の Dashboard 設定の代行変更
- スキーマ全体の自動比較ワークフローの新設(必要なら別 Issue)
