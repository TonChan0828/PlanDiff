# 依存関係の脆弱性対応

仕様書: [G-109](../specs/G-109_Dependabotによる脆弱性の継続検知.md)

CI の `npm audit --audit-level=high` は CI が走ったときしか見ない。PR のない期間に公開された脆弱性は、GitHub の Dependabot で継続的に検知する。

## 有効にしている仕組み(2026-11-24)

- Dependabot アラート(`vulnerability-alerts`): 依存の既知の脆弱性を検知して通知する
- Dependabot セキュリティ更新(`automated-security-fixes`): 修正版がある脆弱性に対して更新 PR を自動作成する
- `.github/dependabot.yml`
  - `github-actions`: 週1回、SHA 固定の更新を1つの PR にまとめる
  - `npm`: バージョン更新 PR は作らない(`open-pull-requests-limit: 0`)。セキュリティ更新だけが PR になる

確認コマンド(`gh` に admin 権限が必要):

```
gh api repos/TonChan0828/PlanDiff -q .security_and_analysis.dependabot_security_updates.status   # enabled
gh api repos/TonChan0828/PlanDiff/vulnerability-alerts -i | head -1                               # 204
gh api 'repos/TonChan0828/PlanDiff/dependabot/alerts?state=open&per_page=100' -q length            # 未解決アラート数
```

## 通知先

- Dependabot アラートは、リポジトリ所有者(admin)の GitHub 通知とメールに届く。通知の設定は GitHub の Settings → Notifications → Dependabot alerts で確認する
- 受け取った人が、下の判断基準に沿って対応を決め、結果をこのリポジトリの `docs/logs/` に残す

## 対応判断の基準

| 重大度 | 判断 |
|---|---|
| critical / high | 直ちに対応する。S 系の仕様書(例: [S-6](../specs/S-6_Next.js_16.4.6への更新.md))を作り、更新して公開する。CI の `npm audit --audit-level=high` も high 以上で止まる(情報源が違うため、判定が一致しないことがある) |
| moderate | 週次で確認する。**本番依存**で、アプリが該当経路を使っているなら対応する。**開発依存のみ**、または該当経路を使わないなら、理由を記録して保留してよい(Dependabot の「却下」には理由を選んで残す) |
| low | 四半期ごとにまとめて確認する |

- 判断の根拠として、`npm audit` の到達経路(`npm ls <package>`)と、アプリが該当機能を使っているかを確認する
- 保留した指摘は、再確認する日付とともに `docs/logs/` に記録する
- CI の監査閾値(`high`)は変えない。moderate は CI を止めず、アラートで拾う

## Dependabot の PR の扱い

- Dependabot の PR も通常の PR と同じく、必須の CI 3ジョブ(`check` / `Integration and migration tests (local Supabase)` / `Mobile browser tests (local Supabase)`)を通す
- `github-actions` の更新 PR は、変更後の SHA が公式リポジトリのタグと一致するかを確認してからマージする(SHA 固定の目的は、タグの付け替えによる混入を防ぐこと)
- 依存の更新に伴う推移依存の変化は、`package-lock.json` の差分で確認する
